# Day31 — ассистент по документам

Проверка: 15.10.2026. Задание сохранено без сокращений в `DAY31_DOCUMENT_ASSISTANT_TASK.txt`.

## Реализация и архитектура

Команда разбирается в `ChatSessionService.execute` (`rag_arbiter/application/chat.py`), после сохранения обычного ChatTurn и до работы с памятью/RAG. `/help` без аргументов читает реестр без LLM. `/help <вопрос>` вызывает новый типизированный метод `AnswerModeRouter.assistant_intent` через существующий `structured` и существующий llm_factory. Результат проверяется схемой `AssistantIntent`: DOCUMENT_CONTENT / ARCHIVE_STATUS, вид сведений реестра, явно названные документы, confidence. Цепочек распознавания ключевых слов в production нет; низкая уверенность или некорректная схема требуют уточнения.

DOCUMENT_CONTENT продолжает тот же Chat, TaskState, ReferenceResolver, ContextualQueryBuilder, RetrievalPolicy, AnswerModeRouter, Point RAG / Exhaustive, grounding и source navigation. Вторых embedding/RAG/Chat/Qdrant/reranker/context builder/LLM provider нет. Для полного охвата и сопоставления документов сохраняется Exhaustive; Point RAG не называется исчерпывающим.

ARCHIVE_STATUS читает существующие Source/Document/Sync/processing/index registries через `ArchiveStatusProvider`. Шаблоны и LLM не обращаются к SQLite. Счётчики, новые файлы, последний scan, ожидание, ошибки и известные папки вычисляются кодом; LLM выбирает только тип запроса. В модель классификации передаётся вопрос и схема, не содержимое реестра. Справка выводит реальные возможности, область, источники, счётчики, ошибки и примеры. Ссылки ведут к существующим документам.

## Область поиска и готовность

Поддержаны выбранный ручной корпус вместе с сетевыми документами, ручной корпус, все сетевые источники и один источник. Область применяется уже при сборке canonical snapshot, затем пересекается с RetrievalPolicy до retrieval. Явные имена файлов разрешаются только внутри текущей области; отсутствующее/неоднозначное имя вызывает уточнение. Сравнение двух именованных документов ограничивает допустимые document IDs этими двумя файлами.

Сведения архива фильтруются тем же source scope. Статусы DISCOVERED, QUEUED, PROCESSING, INDEXED, FAILED различаются; MISSING сохраняется отдельно. INDEXED подтверждается активным canonical manifest, index_runs и существующими chunks, а не одной строкой SUCCESS в network_files. Неуспешные ручные загрузки не теряются в счётчиках частично успешного run.

`/help` о состоянии не меняет TaskState/DialogueWorkingContext. Такие turns исключаются из истории доказательств содержательных запросов. Содержательный `/help` сохраняет обычную память и follow-up. После смены source scope сохраняется прежняя защита через scope_version и сброс рабочего контекста.

## Автоматическое сканирование и безопасность

Основная конфигурация автосканирования остаётся выключенной. В изолированном REAL SMB E2E существующий scheduler SyncService был включён, самостоятельно обнаружил созданный после исходного пустого scan файл и завершил ingestion/indexing. После проверки расписание тестового экземпляра выключено. `/help` не запускает full scan: число scan IDs до/после ответа о состоянии совпало.

MCP остаётся read-only; root allowlist, reparse/final-handle проверки сохранены. LLM не получает файловые инструменты. Служебные каталоги и `.env`, credentials/secrets дополнительно запрещены и при прямом чтении через connector, не только при перечислении. Тестовый сценарий создаёт только уникальный синтетический файл в ранее разрешённой подпапке. Настоящие тексты документов пользователя и credentials в отчёт и облачные проверки не включены.
