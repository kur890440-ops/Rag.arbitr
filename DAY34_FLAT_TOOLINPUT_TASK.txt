==================================================
1. ROOT CAUSE
==================================================

Реальная MiniMax вернула:

{
  "operation": "search_documents",
  "query": "субагентский договор"
}

Provider status: SUCCESS.

Backend ожидал:

{
  "tool": {
    "operation": "search_documents",
    "query": "субагентский договор"
  },
  "done": false
}

Возник Pydantic ValidationError.

В текущем transport нет доказанного
серверного принуждения JSON Schema.

Поэтому одних prompt instructions
недостаточно для гарантии формата.

Проверь фактическую схему

==================================================
3. CANONICAL CONTRACT
==================================================

Единственный внешний контракт:

FLAT TOOLINPUT.

Пример:

{
  "operation": "search_documents",
  "query": "субагентский договор"
}

Не требовать вложенные поля:

tool
arguments
done

Использовать существующую Pydantic
discriminated union по operation,
если она уже подходит.

Каждая операция должна иметь
свою строгую схему аргументов.

Запретить:

- неизвестные operation;
- дополнительные поля;
- отсутствующие аргументы;
- неправильные типы;
- недопустимые значения.

Не добавлять свободный JSON parser,
regex extraction или альтернативный
decoder с угадыванием формата.

Внутренний NextTool, если необходим,
формировать после успешной
валидации Flat ToolInput.

==================================================
4. TASK COMPLETION
==================================================

Не смешивать model tool call
и внутренний статус задачи.

Для завершения допускается
типизированная операция:

{
  "operation": "finish_task"
}

Только если это действительно
нужно существующему Planner.

Backend самостоятельно проверяет:

- выполнена ли цель пользователя;
- создан ли нужный файл;
- выполнены ли обязательные операции;
- сохранена ли рабочая редакция;
- выполнена ли validation;
- доступны ли результаты;
- зафиксированы ли ограничения.

При невыполненной цели:

PARTIAL / FAILED

Нельзя считать finish_task
доказательством выполнения.

Не требовать лишнего вызова MiniMax,
если backend может безопасно
завершить задачу самостоятельно.

==================================================
5. UNIFIED MODEL SCHEMA

Не оставлять конфликтующие инструкции
NextTool/ToolInput в разных частях prompt.

Использовать один контракт
для всех операций.

==================================================
8. REAL PROTOCOL PROBE
==================================================

После успешных offline tests
выполнить максимум 2 реальных
вызова MiniMax.

Использовать настоящий production
prompt, schema и decoder.

Проверить:

1. Получен Flat ToolInput.
2. Pydantic validation PASS.
3. Operation распознана.
4. Аргументы соответствуют схеме.
5. Нет вложенной формы NextTool.
6. Нет угадывания JSON.
7. Tool безопасно готов к исполнению.

В protocol probe файловые
мутации не выполнять.

Если FAIL:

сохранить сырой provider response,
схему, errors и остановиться.

Не запускать полный E2E.

==================================================
9. REAL E2E
==================================================

Только после PASS protocol probe
выполнить один контролируемый E2E.

Использовать существующий harness
из предыдущей задачи, актуализировав
его только при необходимости.

Проверить во внутреннем /chat:

A.

"Найди субагентские договоры,
сравни условия отчетности
и подготовь документ DOCX".

Ожидается:

- автоматический поиск;
- чтение минимум трёх документов;
- использование закреплённых версий;
- анализ;
- создание настоящего DOCX;
- structural validation;
- semantic validation;
- скачивание;
- сохранение task progress.

B.

"Возьми подготовленное заключение,
добавь раздел с различиями
и сохрани новую редакцию".

Ожидается:

- использование результата A;
- новая редакция;
- сохранение исходника;
- diff;
- validation;
- provenance.

C.

Проверить вопросы:

"У кого отличаются условия отчетности?"

"Что известно о Ледневе?"

Убедиться:

- сохранён корректный документный scope;
- новый объект не блокируется;
- retrieval запускается;
- соблюдается ACL;
- цитаты соответствуют источникам.

D.

Проверить доступность новой версии
ранее опубликованного тестового
документа через внутренний RAG.

Если требуется новая публикация,
использовать только тестовую SMB-папку.

Не дублировать опасные операции,
уже имеющие достаточные доказательства.

E.

Проверить обычный ответ /consult
без доступа CLIENT к File Tools.
