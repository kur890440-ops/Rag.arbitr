# DAY 29 · TASK-SPECIFIC LOCAL LLM OPTIMIZATION

Этот документ заменяет прежнее решение об абстрактной лаборатории свободных вопросов как основном режиме Day29. Исторические отчёты и результаты сохраняются, но не определяют текущую задачу.

## TARGET TASK

Day29 оптимизирует локальную LLM под одну конкретную задачу проекта: СТРУКТУРИРОВАННЫЙ АНАЛИЗ СУДЕБНОГО АКТА. RAG в Day29 не используется.

Input: полный нормализованный текст одного судебного документа.

Output:
1. Суть спора.
2. Требования заявителя / истца.
3. Позиция другой стороны, если она есть в документе.
4. Установленные судом обстоятельства.
5. Мотивировка суда.
6. Итоговое решение / резолютивная часть.
7. Ключевые суммы, даты и факты, только если они присутствуют в документе.

Модель не должна:
- придумывать отсутствующие сведения;
- добавлять внешние знания;
- заменять содержание документа общими юридическими рассуждениями.

## INPUT SOURCE

Использовать существующие нормализованные документы rag.арбитр. НЕ использовать Qdrant, retrieval, reranker, chunks, RAG context. Выбранный судебный документ загружается напрямую из canonical normalized content.

Выбор фиксирует recognition version. Перед запуском сервер проверяет SHA-256 просмотренного текста. Полный текст копируется в run при постановке задачи, поэтому последующее изменение canonical record не меняет уже созданный эксперимент. Чтение из normalized_documents не зависит от наличия векторного индекса или активного корпуса. Неполный документ и превышение доступного окна приводят к явной ошибке без скрытого сокращения.

## DAY29 FLOW

Selected judicial document → normalized full text → Day29 task prompt → LocalLLMProvider → structured analysis → metrics.

## OPTIMIZATION

Сравнивать под ЭТУ ЖЕ задачу:
- prompt;
- temperature;
- num_ctx;
- num_predict;
- quantization Q4_K_M vs Q8_0;
- другие реально поддержанные параметры.

Все эксперименты должны использовать ОДИН И ТОТ ЖЕ текст документа. В UI доступны фактические текст, его SHA-256 и версия, prompt и параметры. FAIR требует равенства полного текста, SHA-256, task version и полного task input. Для отличающихся документов/задач performance delta не показывается.

## QUALITY CRITERIA

Оценивать:
- правильно ли определена суть спора;
- правильно ли выделены требования;
- не потеряны ли существенные обстоятельства;
- правильно ли передано решение суда;
- сохранены ли суммы и даты;
- отсутствуют ли выдуманные факты;
- соблюдается ли структура;
- нет ли лишней воды.

Дополнительно оценивать generation time, tokens/sec, RAM, VRAM, input/output tokens.

В каждой завершённой колонке доступна сохраняемая ручная оценка каждого критерия: не оценено / да / частично / нет, с комментарием. Источник оценки явно manual; технический SUCCESS не означает правильность анализа. Нет автоматического утверждения «качество лучше» по скорости или размеру ответа.

## BASELINE VS OPTIMIZED

Baseline: текущий prompt + текущие параметры + Q4_K_M. Существующий system prompt day29-baseline сохранён без изменения; общий user task задаёт семь разделов и полный документ. Форма берёт параметры из актуального local config, не из выдуманной рекомендуемой конфигурации.

Optimized: улучшенный task-specific prompt + подобранные параметры + выбранная quantization. Новый вариант day29-judicial-v1 отдельно требует различать требования сторон, установленные судом факты, мотивировку и резолютивную часть, сохранять суммы/даты/отрицания и не добавлять внешние сведения. Его превосходство не объявляется доказанным до ручной оценки на том же документе.

Сравнение показывается колонками рядом, с горизонтальной прокруткой; на мобильном — вертикально. Baseline выбирает пользователь, выбор хранится в браузере. Варианты параметров и prompt меняются вручную. Старые свободные и RAG runs доступны только через отдельный архив основной вкладки и не включаются в новые сравнения по умолчанию.

## Уточнение проверки размера входа (2026-10-10)

Day29 для установленной Qwen3 использует реальный vocabulary и merges из Ollama `/api/show` с `verbose=true`, проверяя family, tokenizer model/pre и hash поддержанного chat template. Одно и то же правило действует перед созданием запуска и внутри LocalLLMProvider: BPE tokens(system + user) + 512 токенов резерва шаблона + num_predict <= num_ctx. Полный canonical text и prompt не обрезаются. Cache токенизатора привязан к endpoint и digest модели, а не только к exact tag; не более четырёх записей. Q4_K_M и Q8_0 берут собственные metadata, новые модели не добавляются.

В run сохраняется input_budget с методом, digest, резервами и остатком; в карточке виден расчёт. Это предварительный бюджет, не точный prompt_eval_count: фактическое число входных токенов по-прежнему берётся из ответа Ollama. Для неподдержанного tokenizer/template сохранён явно обозначенный `utf8_bytes_upper_estimate`; отсутствие необходимых metadata поддержанной модели не разрешает отправку без проверки.
