ЗАДАЧА

Завершить Day31.

Превратить существующую интеграцию
сетевых документов через MCP
в полноценного ассистента по документам.

В существующем Chat реализовать:

/help
/help <вопрос>

Ассистент должен отвечать
на вопросы о содержании документов,
структуре архива и состоянии индексации.

==================================================
1. INSPECT FIRST
==================================================

Сначала изучи существующий код:

- Chat handlers;
- ChatSession;
- AnswerModeRouter;
- RetrievalPolicy;
- Point RAG;
- Exhaustive mode;
- ContextBuilder;
- grounding/citations;
- source selection;
- MCP File Connector;
- Source SyncService;
- Source Registry;
- Document Registry;
- canonical storage;
- PDF/DOCX ingestion;
- indexing status;
- существующий Chat UI.

Проверь, что уже реализовано
по предыдущим задачам Day31.

Не дублируй работающие функции.

==================================================
2. COMMAND /help
==================================================

Добавить обработку команды
в existing Chat input.

Без аргументов:

/help

Показать:

- назначение ассистента;
- выбранную область поиска;
- доступные источники;
- количество обнаруженных документов;
- количество проиндексированных;
- количество ожидающих;
- ошибки источников;
- примеры вопросов.

Данные брать из существующих реестров.

Не генерировать фиктивные счетчики.

==================================================
3. COMMAND /help <QUESTION>
==================================================

Примеры:

/help Что предусматривает
агентский договор?

/help Какие документы регулируют
страховые выплаты?

/help Сравни условия договоров.

/help Что нового появилось в архиве?

/help Какие файлы еще не обработаны?

Поддержать русскоязычные вопросы.

==================================================
4. REUSE CHAT PIPELINE
==================================================

/help не должен создавать
второй Chat или второй RAG.

Для вопросов по содержанию:

/help question
→ existing Chat orchestration
→ existing RetrievalPolicy
→ existing Point/Exhaustive selection
→ existing RAG
→ existing grounding/citations.

Не создавать отдельные:

embedding service
Qdrant index
reranker
context builder
LLM provider.

==================================================
5. QUESTION ROUTING
==================================================

Различать два типа запросов:

DOCUMENT_CONTENT

ARCHIVE_STATUS.

DOCUMENT_CONTENT:
поиск и ответы по canonical documents.

ARCHIVE_STATUS:
чтение актуального Source/Sync registry.

Использовать существующий
semantic/typed routing mechanism,
если он подходит.

Не строить большую цепочку
keyword/regex условий.

Явная команда /help
разбирается детерминированно.

Router не выполняет OCR,
не сканирует сеть
и не изменяет документы.

==================================================
6. ARCHIVE STATUS PROVIDER
==================================================

Создать или переиспользовать
read-only application-level API
для чтения:

sources
folders
files
scan runs
document statuses
ingestion statuses
index statuses.

Не обращаться напрямую к SQLite
из template или LLM prompt.

Статусы брать из фактических записей.

==================================================
7. DOCUMENT CONTENT
==================================================

Вопросы о документах должны
использовать existing RAG.

Например:

"Какие обязанности агента
предусмотрены договором?"

Ожидается:

- релевантные положения;
- структурированный ответ;
- точные цитаты;
- название документа;
- переход к источнику.

Не заменять поиск
общими знаниями модели.

==================================================
8. MULTI-DOCUMENT QUESTIONS
==================================================

Поддержать:

- сопоставление договоров;
- поиск различий;
- выявление противоречий;
- обобщение по нескольким файлам.

Для вопросов о конкретных
нескольких документах
ограничивать поиск ими.

Для вопросов вида:

"Какие документы во всем архиве
содержат такие условия?"

использовать exhaustive,
если требуется полный охват.

Не объявлять Point RAG
исчерпывающим поиском.

==================================================
9. SOURCE SCOPE
==================================================

/help использует текущие
ограничения ChatSession.

Все документы
Сетевые источники
Загруженные вручную
Конкретный источник.

Фильтр применяется до retrieval.

Для ARCHIVE_STATUS
ограничивать возвращаемый реестр
тем же scope.

Не показывать документы
из других выбранных областей.

При изменении scope
старые ответы не становятся
новым доказательством.

==================================================
10. PROVENANCE
==================================================

Для каждого содержательного ответа:

document ID
document name
source ID
page/section/block
evidence quote.

PDF:
реальный номер страницы.

DOCX:
структурный блок/раздел.

Не придумывать пагинацию DOCX.

Использовать existing source navigation.

==================================================
11. CHAT UI
==================================================

Не создавать новую страницу.

В существующем Chat добавить
компактную подсказку:

"Вопросы по документам: /help"

При вводе /help
показывать результат

- текст;

- структурированные сведения

Не выводить raw JSON пользователю.

13. AUTOMATIC SCAN
==================================================

Использовать существующее расписание
Source SyncService.

Проверить, что автоматический scan
фактически запускается.

Если есть ошибка:
показать ее причину.

Не запускать full scan
при каждом сообщении /help.

Команда /help по умолчанию
только читает состояние архива.

==================================================
14. READ_ERROR
==================================================

В предыдущем реальном источнике
наблюдалось:

READ_ERROR.

Проверить актуальное состояние.

Если ошибка сохранилась:
определить конкретную причину.

Исправить подтвержденный дефект
без обхода root allowlist
и без ослабления безопасности.

Не скрывать READ_ERROR.

Не интерпретировать ошибочный scan
как отсутствие документов.

==================================================
15. DOCUMENT READINESS
==================================================

Различать:

DISCOVERED
QUEUED
PROCESSING
INDEXED
FAILED.

Только документы с подтвержденным
активным индексом
участвуют в Point RAG.

Для exhaustive использовать
существующие правила допустимости
canonical content и готовности данных.

Не утверждать, что любой
обнаруженный файл уже доступен
для ответов.

==================================================
16. NORMAL LANGUAGE
==================================================

при последнем сканировании?

"При последнем сканировании
обнаружены 3 новых документа:

...

2 документа проиндексированы.
1 ожидает обработки."

Это пример формата,
не реальные данные.

==================================================
17. FOLLOW-UP
==================================================

Сохранить существующую
семантику Chat follow-up.

Должен корректно разрешаться

22. REAL E2E DEMONSTRATION
==================================================

Выполнить реальный сценарий
для разрешенной сетевой папки.

1. Проверить подключение SMB/NAS.

2. Подтвердить успешный MCP scan.

3. Обнаружить новый PDF/DOCX.

4. Выполнить ingestion.

5. Проверить canonical content.

6. Проверить chunks и Qdrant index.

7. Убедиться, что Chat показывает INDEXED.

8. Выбрать конкретный сетевой источник.

9. Выполнить:

/help <вопрос по документу>

10. Получить grounded answer
с проверенной цитатой.

11. Выполнить:

/help Какие документы
обнаружены при последнем scan?

12. Сверить ответ
с реальными данными SyncService.

13. Повторить scan.

14. Подтвердить,
что unchanged documents
не обрабатывались повторно.

Если реальный SMB или LLM
недоступны, честно отметить
непроведенные шаги.
