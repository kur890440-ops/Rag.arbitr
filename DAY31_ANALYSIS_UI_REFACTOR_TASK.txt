ЗАДАЧА

Переделать текущий UI.

Проблема:
мы построили интерфейс, похожий
на файловый менеджер:

- дерево папок;
- поиск по именам;
- множество фильтров;
- таблица файлов;
- отдельная навигация по архиву.

Но назначение rag.арбитр —
поиск информации и анализ документов.

Нужно убрать избыточные элементы,
не потеряв полезные функции.

==================================================
1. INSPECT FIRST
==================================================

Изучи:

- текущий Document Catalog;
- Sources UI;
- Chat UI;
- документный реестр;
- source scope;
- ChatSession;
- RetrievalPolicy;
- переход "Обсудить в Chat";
- существующие API и templates.

Переиспользовать работающий код.

Не создавать второй document selector
или вторую систему фильтрации.

==================================================
2. REMOVE CATALOG TAB
==================================================

Убрать "Каталог документов"
из основной навигации.

Убрать как основные элементы:

- дерево папок;
- файловую навигацию;
- отдельный поиск по имени;
- сложную таблицу каталога;
- фильтры файлового менеджера.

Существующие API и данные
не удалять автоматически.

Если на Catalog есть внешние ссылки,
обеспечить корректный переход
в Chat или Sources.

Не ломать переходы к документам.

==================================================
3. SOURCES TAB
==================================================

Оставить управление документными
источниками на существующей вкладке.

Главный экран:

ИСТОЧНИКИ ДОКУМЕНТОВ

Источник           Статус
Доки               Подключен

Обнаружено:         N
Проиндексировано:   N
В обработке:        N
Ошибки:             N

Последний scan: ...
Следующий scan: ...

[Сканировать сейчас]

Подробности обработки и ошибки
можно раскрывать по необходимости.

Не нужно постоянно показывать
всё дерево сетевого диска.

==================================================
4. CHAT MAIN SCREEN
==================================================

Chat должен выглядеть как Chat.

Основная компоновка:

Слева:
история диалогов.

В центре:
сообщения пользователя;
ответы;
цитаты;
поле ввода.

Справа:
существующая сворачиваемая
память задачи.

Над сообщениями:

Область анализа:
[Все документы ▼]

[Выбрать документы]

Не показывать большие таблицы,
состояние сканирования
или дерево каталогов
над диалогом.

==================================================
5. ANALYSIS SCOPE SELECTOR
==================================================

Доступные варианты:

- Все документы
- Сетевые источники
- Загруженные вручную
- Конкретный источник
- Выбранные документы

Использовать existing scope model
и RetrievalPolicy.

Не создавать параллельную реализацию.

==================================================
6. DOCUMENT SELECTION
==================================================

Кнопка:

[Выбрать документы]

Открывает компактную панель
или модальное окно.

Внутри:

- название документа;
- источник;
- формат;
- количество страниц/блоков,
  если известно;
- индикатор готовности;
- checkbox.

Разрешить выбрать несколько документов.

Предусмотреть:

[Выбрать все доступные]
[Снять выбор]
[Применить]

Для больших архивов
использовать пагинацию или
ленивую загрузку.

Можно оставить поиск по названию
ВНУТРИ панели выбора,
но не как основную функцию приложения.

==================================================
7. ONLY READY DOCUMENTS
==================================================

Для анализа выбирать только документы,
которые действительно готовы
к соответствующему RAG-режиму.

Не считать INDEXED только по
текстовой отметке в UI.

Проверять реальное состояние
активного индекса/chunking run.

Необработанные документы
можно показывать с пояснением,
но нельзя включать их в retrieval
как будто они готовы.

==================================================
8. SELECTED DOCUMENTS
==================================================

После применения показать
компактную строку:

Анализ: 5 документов

[Изменить] [Сбросить]

При выборе одного документа:

Анализ: Агентский договор.docx

Не занимать большую часть экрана
списком выбранных файлов.

==================================================
9. APPLY TO RAG
==================================================

КРИТИЧЕСКИ:

Выбор документа должен менять
реальную область поиска.

Например:

selected_document_ids = [A, B, C]

Тогда Point RAG ищет
ТОЛЬКО среди A, B, C.

Фильтрация должна происходить
ДО candidate_top_n.

Exhaustive также ограничивается
этими документами.

Нельзя:

- фильтровать только в UI;
- просить LLM игнорировать
  остальные документы;
- незаметно расширять область
  при отсутствии результатов.

==================================================
10. SESSION PERSISTENCE
==================================================

Выбор области сохранять
в существующей ChatSession.

При повторном открытии чата
выбор должен восстановиться.

При создании нового чата
применять явный scope нового чата
или существующее правило наследования.

Не менять выбор во всех чатах сразу.

При изменении scope сохранять
существующие правила revalidation
предыдущих claims и citations.

==================================================
11. DISCUSS DOCUMENT
==================================================

Сохранить полезное действие:

"Обсудить документ".

Из существующего реестра,
просмотра документа или Sources
можно перейти в Chat.

При этом создаётся/выбирается
ChatSession с явным document scope.

Не использовать имя файла
как поисковую инструкцию.

==================================================
12. ANSWERS AND CITATIONS
==================================================

В Chat показывать:

- содержательный ответ;
- подтверждающие цитаты;
- названия исходных документов;
- возможность открыть источник.

PDF:
реальная страница.

DOCX:
раздел или структурный блок.

Существующий grounding
не менять.

13. /help
==================================================

Команда /help остаётся.

Вопросы по документам
идут в существующий RAG.

Вопросы о состоянии архива
используют Source/Sync Registry.

Не создавать отдельный Agent.

==================================================
14. UX / LAYOUT
==================================================

Уменьшить число вложенных
областей прокрутки.

Центральная область Chat —
главное рабочее пространство.

Панель выбора документов
открывается только по запросу.

Интерфейс должен оставаться удобным
при сотнях и тысячах документов.

Использовать существующий UI stack:

FastAPI
Jinja2
HTMX
CSS.

Без новых frontend frameworks.

==================================================
16. E2E SCENARIO
==================================================

Проверить пользовательский сценарий:

1. Открыть "Источники документов".
2. Убедиться, что документы
   обнаружены и проиндексированы.
3. Открыть Chat.
4. Нажать "Выбрать документы".
5. Выбрать два DOCX.
6. Задать вопрос об условиях договоров.
7. Получить ответ с цитатами.
8. Проверить, что другие документы
   не попали в retrieval.
9. Сбросить выбор.
10. Убедиться, что полный корпус
    снова доступен при соответствующем scope.

Если реальная генерация недоступна,
отдельно отметить это,
не выдавать mock за E2E.

==================================================
17. ACCEPTANCE
==================================================

Главный экран больше не должен
выглядеть как файловый менеджер.

Пользователь должен:

- подключить источник;
- увидеть состояние индексации;
- выбрать документы;
- задать вопрос;
- получить проверяемый ответ.

Это основной сценарий rag.арбитр.
