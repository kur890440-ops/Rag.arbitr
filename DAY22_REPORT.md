## Действующее решение 2026-10-01: FINAL RAG + NO-RAG refactor

Один вопрос и три панели сохранены. Реализация и локальная проверка завершены; два новых полных внешних сравнения пока не выполнены по причине, указанной в п. 28. Результаты предыдущих этапов ниже сохранены как история.

### A. EXHAUSTIVE NO-RAG

1. **Batcher.** `ExhaustiveContextBatcher` читает версионные нормализованные документы; стабильная сортировка document/page/block. Предпочитает целые блоки, крупные делит без overlap, сохраняет позиции и пустые страницы. Каждый пакет проверяется вместе с инструкцией, вопросом и резервом output. Маленькая область передаётся целиком одним запросом.
2. **100% coverage.** Область — выбранный документ либо весь текущий корпус. Страница считается покрытой только после успеха всех её пакетов; документ — всех страниц. Потерянный/ошибочный пакет даёт PARTIAL. BGE-M3=0, Qdrant=0, Top-K и similarity filtering отсутствуют в этой ветке; это проверено запретительными mocks.
3. **Independent map.** Каждый вызов получает исходный вопрос и только свой пакет; нет history, previous result или iterative refine. Map temperature=0, отдельный extraction prompt. `BatchExtractionResult` дополнен `documents` и `pages`, включая чтение старого кеша; сохраняются findings/evidence/limitations/status. Финальные ответы всех трёх веток используют одну текущую модель и совместимые настройки.
4. **Merge/count.** Код нормализует ключи NFKC/casefold/пробелы, объединяет evidence, считает уникальные позиции цитат и разные document_id. Повтор того же finding не увеличивает счётчик. Это частоты извлечённых свидетельств, не гарантия полного понимания моделью.
5. **Order invariance.** Тест normal/reverse/seed42 на одинаковых extraction results даёт одинаковые findings/counts. Сохранён предыдущий реальный диагностический результат: перестановка фиксированных real results даёт один digest, но новые независимые LLM вызовы дали 8/9/7 findings. Кеш стабилизирует повторное использование; абсолютная воспроизводимость свежих LLM extraction не обещается.
6. **Final MiniMax.** Получает вопрос, coverage, merged findings, counts, representative quotes, limitations. Исходный корпус повторно не передаётся. Если все findings не помещаются, явный PARTIAL/SYNTHESIS_BUDGET_EXCEEDED; скрытой выборки нет. Общие final settings не заменяются map settings.
7. **Real tokens/requests/time.** Новое полное внешнее сравнение не запущено: разрешение на все 16 документов ожидается. Фактических новых API tokens/time/answers нет. Предыдущий локальный preview: 16 документов, 90 страниц, 18 map-пакетов, обычно 19 exhaustive requests без retries/cache; это план, не измерение API. UI отдельно показывает map requests и общее число запросов.

### B. POINT RAG

8. **До refactor.** Одно Top-K одновременно определяло ширину retrieval и максимум чанков для прямого context builder.
9. **Теперь.** BGE query → Qdrant active candidates → exact/near-overlap dedup → doc/section grouping → bounded parent/neighbor expansion → soft diversity + budget selection → final ContextCandidates → RAGContextBuilder → MiniMax. Expansion строит альтернативы, selector выбирает их с учётом разнообразия и бюджета.
10. **candidate_top_n.** Default 20, диапазон 1–100, root config/API/UI/CLI. В Qdrant передаётся именно это число.
11. **max_context_sources.** Default 5; при отсутствии root-настройки берётся legacy `top_k`. Диапазон 1–20. API/CLI `top_k` остаётся явным alias, конфликтующие значения отклоняются.
12. **Exact dedup.** Повторы chunk_id и content_hash исключаются после стабильной сортировки score/rank/id; причины сохранены. Неактивные чанки отбрасываются дополнительно перед expansion.
13. **Overlap dedup.** Внутри документа сравниваются нормализованные word 5-grams: containment ≥0.90 и отношение длин ≥0.8. Короткие тексты требуют точного совпадения слов. Обычное частичное пересечение сохраняет новый материал. Порог релевантности по умолчанию выключен.
14. **Grouping.** По document_id/section; совпавшие expanded contexts объединяют anchor IDs/original ranks. Сохраняются score и активные ChunkingRun identities.
15. **Diversity.** Greedy selection уменьшает приоритет повторного документа на 0.04 и повторной секции ещё на 0.02. Параметр configurable, это эвристика, не доказанный оптимум. Нет max-one-document: разные полезные контексты одного документа допустимы.
16. **Structure parent.** Только блоки текущей активной partition/version, непрерывная одноимённая секция, содержащая anchor blocks. Разумный размер ограничен expansion budget (default 6000 UTF-8 bytes). Секция из всех блоков документа не расширяется автоматически до whole document.
17. **Fixed neighbors.** Только непосредственные индексы previous/next того же документа и версии с соприкасающимися char ranges. Сосед должен быть retrieval candidate либо иметь общую секцию и исходный блок с anchor. Проверяются размер и запрет автоматического охвата целого документа. Точное суффикс/префикс пересечение удаляется.
18. **Budget.** Selector проверяет полную сериализацию headers+text, не только текст. Не более max sources и context budget. Слишком большой parent пробует fallback на anchor; если и он не помещается — пропускается. Оценка UTF-8 bytes консервативна, это не tokenizer MiniMax; число фактических API tokens отдельно.
19. **Реальный локальный пример.** Вопрос о резолютивной части, Structure: `20 raw → 20 after dedup → 19 contexts built → 5 contexts used`; 8 документов среди кандидатов, 5 в итоговом контексте, 4656 estimated tokens. Это реальный BGE/Qdrant поиск без вызова внешней LLM. Артефакт: `data/day22/candidates/local-retrieval.json`.
20. **No vectors to MiniMax.** Query embedding используется только retrieval. LLM получает вопрос и обычные тексты [S1]… с file/section/pages; не получает vectors, все raw candidates или Qdrant internals. Проверено provider/context tests.
21. **No whole-document auto-send.** Матч запускает ограниченное расширение секции/соседей, а не full-document builder. Сам anchor может совпасть с коротким документом — это не автоматическое добавление всего найденного файла.
22. **Factual real test.** Вопрос: «Кто указан заявителем в ходатайстве ООО „РУСМЕТ“ от 24 февраля 2025 года?» Нужный source на rank 1 в обоих индексах при N=5 и N=20. В Structure первым идёт parent section ходатайства 24.02. Ожидание: ИО конкурсного управляющего Погосян Лилия Гамлетовна. Новый LLM answer не получен: внешний этап ожидает согласия, локальный retrieval не выдаётся за answer-quality test.
23. **Corpus-wide question.** По вопросу о резолютивной части Structure N=20 дал контексты из 5 документов, Fixed — из 2. Это выборочные контексты, не обзор 16/16. В UI прямо указано отсутствие гарантии полного обзора у RAG. Новый exhaustive answer с 100% coverage пока не получен.
24. **Experiment 5 vs 20.** max_context_sources=5, budget=12000 неизменны. Structure factual: N5 → 4 sources/3 docs/11022 bytes; N20 → 5 sources/5 docs/10738 bytes. Rank правильного документа 1 в обоих. Retrieval+processing 96.1/106.6 ms плюс общий query embedding 284.6 ms. Fixed: оба дают 2 sources/2 docs/9926 bytes, rank1, 25.8/104.1 ms. Это один локальный прогон, не статистический benchmark; улучшение ответа не установлено. Подготовлен `scripts/check_final_rag_real.py`: основной factual N20 comparison, N5 RAG-only с reuse exhaustive baseline, затем corpus question. Проверяет совпадение локального и актуального контекста перед reuse.

## История 2026-10-01: независимый exhaustive NO-RAG baseline

Средняя панель теперь **БЕЗ RAG · ПОЛНЫЙ ПРОСМОТР**. Маленький scope сохраняет один прямой запрос. Большой scope полностью проходит независимые map-пакеты, deterministic merge/count и один final synthesis. Отдельного Corpus Analysis UI, пользовательского CorpusAnalysisRun или iterative refine нет. Предыдущее ограничение «только один запрос или CONTEXT_TOO_LARGE» ниже оставлено как история и заменено этим решением.

### Отчёт по 23 пунктам текущего задания

1. **Изменение middle branch.** `RAGComparisonService` переиспользует `FullDocumentContextBuilder`: READY → прежний fast path, слишком большой scope → внутренний `ExhaustiveNoRAG`. NO CONTEXT и retrieval/RAG выполняются прежним кодом. Все ветки остаются в одном comparison record и общем executor.
2. **Лимит большого scope.** Превышение full-context budget больше не означает автоматическую недоступность средней ветки. CONTEXT_TOO_LARGE означает невозможность вместить минимальный пакет вместе с инструкцией/вопросом/output reserve. Ошибки нормализации остаются явными. Если уже объединённые findings не помещаются даже с компактными representative quotes, возвращается PARTIAL / SYNTHESIS_BUDGET_EXCEEDED, без скрытого удаления findings.
3. **ExhaustiveContextBatcher.** `application/exhaustive.py`: сортировка document_id → page_number → reading_order/block_id. Пакеты не пересекают границы документов, что стабилизирует кеш остальных файлов. Блоки сохраняются целиком, если возможно; слишком длинный блок делится по символам, без overlap, с char_start. Пустые страницы имеют маркер. AnalysisBatch содержит batch_id, document_ids, file_titles, page_ranges, section_references, normalized_text, content_hash, estimated_tokens, normalization_version и units.
4. **Coverage.** Каждая страница/документ сопоставлены со всеми содержащими их batch IDs. Covered означает, что успешны **все** эти пакеты. Разрезанная страница не считается полностью покрытой после одного фрагмента. SUCCESS требует всех map results и успешной итоговой генерации. Тест восстанавливает точный исходный текст каждого блока из пакетов; сортировка и разбиение повторяемы.
5. **Independent map.** Один versioned prompt `exhaustive-map-2`; только original question и текущие units. Никаких предыдущих map results, предварительного ответа или conversation history. Во входе используются короткие U1/U2…, сервер сопоставляет их с canonical IDs. Температура map=0; основная модель и параметры финального/левого/правого ответов не меняются. Это поддерживаемое значение согласно [официальной документации MiniMax](https://platform.minimax.io/docs/api-reference/text-openai-api), но не гарантия полной воспроизводимости модели.
6. **Точная schema.** `ExtractionPayload`: relevant: StrictBool; findings: list[ExtractedFinding]; limitations: list[str]. `ExtractedFinding`: unit_id: str; normalized_key: str|null; statement: str (1–4000); category: str|null; evidence_text: str (1–12000). Сервер преобразует это в `Finding`, добавляя document_id, file_title, page:int, section, block_id, char_start:int. `BatchExtractionResult`: batch_id:str; relevant:bool; findings:list[Finding]; evidence:list[dict]; limitations:list[str]; status:str. relevant=false + findings=[] — SUCCESS. Некорректный JSON, неизвестная ссылка или отсутствующая цитата не принимаются.
7. **Merger.** Чистая функция `ExhaustiveEvidenceMerger.merge`: NFKC/casefold/нормализация пробелов для ключей, точная/нормализованная дедупликация по позиции и цитате, стабильные сортировки групп/утверждений/evidence. Без normalized_key группируется нормализованное statement. Разные утверждения с одним ключом сохраняются, включая противоречия; fuzzy semantic merge не выполняется.
8. **Counts.** occurrence_count — число уникальных процитированных вхождений (document/block/offset/quote); document_count — число разных document_id в группе; documents_total — размер scope. Повторная выдача того же finding не удваивает счётчики. Повтор цитаты восемь раз в одном файле даёт восемь вхождений и один документ. Это счётчики извлечённых свидетельств, а не доказательство, что LLM нашла все смысловые факты.
9. **Provenance.** Цитата проверяется как точный substring текущего unit; document/page/section/block/offset заполняет сервер. Все evidence сохраняются. Для final используются стабильные [E1]…; выдуманные номера ссылок отклоняются. На реальном тесте длинные hash IDs путались моделью; короткие локальные aliases устранили эту техническую причину отказа.
10. **Final input.** Original question, coverage, все объединённые ключи/утверждения/счётчики, ограничения и одна representative evidence на группу. Цитата ограничена 500 символами, при необходимости 80; вся provenance остаётся сохранённой. Ни одна группа не выбирается по relevance score и не удаляется ради бюджета. Final prompt требует 1–3 предложения и запрещает неподтверждённые частотные обобщения.
11. **Нет повторной отправки raw corpus.** Final request содержит merged data, не исходные документы. Исходный normalized text идёт только в fast path либо map calls. Raw OCR/Qwen/PDF/images/embeddings не передаются.
12. **BGE-M3 = 0 в exhaustive.** Подтверждено тестом, запрещающим BgeM3EmbeddingProvider.encode и pipeline factory в средней ветке.
13. **Qdrant = 0 в exhaustive.** Подтверждено тестом, запрещающим создание LocalVectorStore. RAG сохраняет свой отдельный вызов vector retrieval.
14. **Нет Top-K.** Бatcher проходит весь scope без similarity, ranking, reranker, BM25, query rewriting или отбора документов. RAG справа остаётся Top-K.
15. **Cache.** `exhaustive_map_cache` и `exhaustive_batch_results`, без отдельной пользовательской сущности. Ключ: question hash, batch content hash, provider/model/generation settings, map version, normalization identity/version, BASE_SYSTEM. Ключ API исключён из сериализации. Успех сохраняется сразу; в batch record хранятся попытки и safe raw diagnostic (provider уже удаляет reasoning/ключ). Все malformed результаты остаются FAILED, не facts. Изменение вопроса, контента, модели/настроек или prompt не использует старый несовместимый кеш.
16. **Resume.** Повторное comparison использует успешные map results, запускает недостающие/failed, затем final synthesis. При разрыве между записью результата и публикацией в cache есть recovery lookup по cache_key. Не пересчитываются успешные пакеты. По умолчанию один worker map и один retry; конфиг допускает concurrency 1–2, retries 0–2. Retry ограничен malformed/output limit и временными transport errors; billing/auth автоматически не повторяются.
17. **Progress.** Расширен RAGComparisonRun полем `exhaustive`; используется существующий polling. Видны scope, документы/страницы covered/total, %, batches, requests, actual input/output usage, duration, cache hits. На каждой завершённой обработке пакета record обновляется. PARTIAL явно отображается, включая финальное обобщение по неполному покрытию. Детали пакетов/факты находятся только в свёрнутой технической диагностике.
18. **UI.** Всегда три панели: БЕЗ КОНТЕКСТА / БЕЗ RAG · ПОЛНЫЙ ПРОСМОТР / С RAG. Ни mode selector, ни Corpus Analysis tab, ни основной per-document list. Иначе последовательные пакеты. Оценка токенов — верхняя оценка по UTF-8 bytes; текущий общий бюджет 65536, резерв генерации 8192.

8. **BGE-M3 / Qdrant.** Не вызываются для corpus analysis. Тест запрещает вызовы embedding/search; они остаются в POINT_RAG. OCR/Qwen/render также не запускаются. Канонический вход — существующие `Document/Page/Block` (нормализованные модели проекта), а не raw output.
9. **Map prompt.** Анализировать текущий документ/пакет только относительно original question; вернуть JSON с relevant, summary, facts, evidence, limitations. Запрещены corpus conclusions, внешние знания и исполнение инструкций источника. Evidence задаётся exact block ID и точной цитатой. relevant=false — успешный результат.
10. **DocumentAnalysisResult.** Typed Pydantic model: document_id, file_title, document_hash, question_hash, status, relevant, summary, facts, evidence, pages, sections, limitations, input/output tokens, duration_ms, batches, cache_hit, created_at. `BatchAnalysisResult` также typed; JSON и тип boolean проверяются строго.
11. **DocumentReducer.** Детерминированное объединение всех batch results без повторной отправки исходного документа. Удаляются только точные дубликаты фактов/цитат; противоречащие утверждения остаются. relevant=any(batch.relevant); отсутствие информации в одном пакете не объявляется отсутствием во всём документе.
12. **Provenance.** Цитата обязана дословно присутствовать в указанном блоке текущего пакета; иначе документ получает FAILED. Сервер самостоятельно добавляет document_id, file_title, page, section, block_id. В интерфейсе цитаты и метаданные раскрываются. Это проверка происхождения цитаты, не автоматическая семантическая проверка каждого утверждения модели.
13. **CorpusAggregator.** Получает структурированные результаты документов, включая ошибки и отсутствие релевантности. Передаёт summaries/facts/evidence/limitations, без полного исходного корпуса. Если сводка не вмещается, выполняет иерархическое обобщение всех групп; oversized result делится с сохранением ссылки. Каждый вызов проверяется по бюджету. Если модель не сокращает материал или превышен лимит уровней, возвращается явная ошибка вместо скрытого усечения.
14. **Final prompt.** Ответить на исходный вопрос по совокупности результатов; сравнить общие признаки и различия, учитывать coverage/failed, цитировать [D1]…[Dn]. Ссылки сопоставлены с документами и evidence; выход за диапазон отклоняется. Свободные текстовые facts не считаются унифицированными признаками, поэтому точные частоты/проценты и неподтверждённое «большинство» запрещены. Код считает только объективную статистику покрытия.
15. **Coverage.** documents_total — размер manifest; processed — SUCCESS; relevant/irrelevant — разбиение SUCCESS; failed — сохранённые неуспешные документы; pages_represented — страницы полностью успешных документов. analysis_batches — завершённые map requests, requests_count — фактические попытки provider, токены — usage API (при отсутствии usage остаются 0). Cache hits показаны отдельно. При failed>0 итог PARTIAL; если ни одного успешного документа — FAILED без ложного обобщения.
16. **Cache.** Таблица `corpus_analysis_cache`. Ключ включает хеш нормализованных страниц/блоков, recognition identity и parser_version, question_hash, provider/model/все несекретные generation settings, prompt_version. Сохраняются только успешные результаты, включая irrelevant. Смена вопроса инвалидирует все; изменение одного документа — только его запись. `corpus_document_analysis_results` фиксирует результат каждого документа данного run; `corpus_analysis_runs` — прогресс и итог. API-ключ не сериализуется.
17. **Resume.** Пропускает уже сохранённые SUCCESS текущего анализа; обрабатывает missing/failed, затем снова агрегирует. Состояния с умершим owner process переводятся в INTERRUPTED при старте сервиса. Состав корпуса и generation settings закреплены в run. Результаты документов сохраняются до финального reduce, поэтому сбой reduce не требует новых map вызовов.
18. **Cancellation.** Cooperative event проверяется между документами, пакетами и reduce requests. Выполняющийся HTTP-запрос не прерывается насильно: остановка после его возврата/timeout. Завершённые документы остаются в SQLite, доступны для resume. При штатном закрытии приложения сигналы отмены устанавливаются до shutdown общего executor.

## Актуальное обновление: RAG по всему корпусу

Выбранный справа файл теперь **не ограничивает RAG автоматически**. Новый default — **Все документы**. Файл задаёт Full Document / viewer / chunking; отдельный переключатель «Область поиска» управляет RAG и исходным semantic search. Разделы ниже описывают предыдущие этапы и сохраняются как история.

### Отчёт по 24 пунктам scope refactor

1. **Прежняя связность.** `web/static/rag.js::ragSettings` отправлял `document_id=selectedDocument`; `RAGComparisonService._execute` передавал его прямо в `SemanticRetriever.retrieve_vector`; retriever собирал document_ids для `LocalVectorStore.search`. Так выбор справа автоматически сужал RAG. Raw semantic search до изменения всегда искал по всему corpus.
2. **Новый поток.** UI отдельно передаёт `selected_document_id` и `rag_scope`. Первый идёт в неизменённую Full Document ветку; `scope.retrieval_document` разрешает фильтр только для явно заданного SELECTED_DOCUMENT. Старый API-параметр document_id принимается как alias выбранного файла, но больше не включает фильтр сам по себе.
3. **RAGScope.** Общий enum `scope.py`: ALL_DOCUMENTS / SELECTED_DOCUMENT. Используется API, comparison service и raw search. Противоречащие друг другу selected_document_id/document_id отклоняются.
4. **Default.** ALL_DOCUMENTS в UI, HTTP API, reusable service и CLI. `rag --document-id ...` задаёт Full Document; для ограничения RAG дополнительно нужен `--rag-scope SELECTED_DOCUMENT`.
5. **ALL query.** Для каждой partition активного индекса: `query_points(collection, vector, limit=K, Filter(must=[chunk_id MatchAny(active_partition_chunk_ids)]))`. Поля document_id в Qdrant filter нет. Результаты partitions объединяются по score, финальный Top-K берётся по всему активному корпусу.
6. **SELECTED filter.** Тот же active chunk whitelist плюс `document_id MatchAny([selected_document_id])`. Partitions без выбранного документа пропускаются. Без файла RAG возвращает DOCUMENT_REQUIRED без BGE/Qdrant, NO CONTEXT продолжает работу. Raw search возвращает понятный HTTP 400 до retrieval.
7. **Current corpus.** Используется snapshot выбранного ProcessingRun с corpus_id, конкретными коллекциями и точными active chunk_ids. ALL означает этот корпус, а не все коллекции Qdrant. Тест с посторонним вектором максимальной близости в используемой коллекции подтвердил исключение до Top-K.
8. **История индексов.** Exact whitelist активных chunk_id применяется непосредственно в Qdrant до limit. Старые чанки могут оставаться на диске, но не участвуют в поиске. Тест сохраняет старый Fixed index и строит новые версии: старые IDs не возвращаются.
9. **Per-file overrides.** Переиспользован `rechunk.partitions`: старые partitions уже исключают заменённые document/chunk IDs; новые содержат актуальную версию изменённого файла. ALL опрашивает все активные partitions. Тест выполняет разные Fixed overrides для двух файлов и проверяет обе текущие версии одновременно.
10. **Payload/identity.** Существующий Qdrant payload содержит chunk_id, document_id, strategy, file_name, source/title, section, pages, content_hash, recognition IDs. Corpus/version identity задаётся существующим snapshot + collection + active chunk whitelist; отдельный payload corpus_id для этого не требуется. Результаты дополнены corpus_id и chunking_run_id из выбранной partition. Vector migration/reindex/OCR не понадобились.
11. **Search tab.** Три панели сохранены; у Full Document указан выбранный файл, у RAG — фактическая область сохранённого сравнения. Отображаются количество активных corpus chunks, документов в Top-K, Top-K/retrieved/used/context/retrieval duration. Source details включают rank, score, file/title, section, pages, chunk ID и активную версию.
12. **Control.** «Область поиска»: «Все документы» / «Выбранный файл». Рядом строка `RAG: область · strategy · Top-K · ChunkingRun`. Дополнительного списка файлов нет. Этот control применяется и к раскрываемому Fixed vs Structure semantic search.

## Обновление: Full Document baseline

Текущая версия добавляет третью ветку **ВЕСЬ ДОКУМЕНТ** между **БЕЗ КОНТЕКСТА** и **С RAG**. Ниже в документе сохранён исторический отчёт первоначального Day 22; его сведения об отсутствии ключа и двух панелях относятся к первоначальной проверке. Сейчас MiniMax M3 через настроенный OpenRouter проверен реальными запросами. Ключ поддерживается в исключённом из Git `config.toml`, поле `[llm].api_key`, либо в окружении `MINIMAX_API_KEY` с приоритетом окружения; `api_key_env` содержит только имя переменной. Секрет исключается из serialization/snapshots/UI.

### Отчёт по 21 пункту Full Document

1. **Переиспользование.** Расширены существующие `LLMRequest`, `MiniMaxLLMProvider`, `RAGComparisonService` и Jinja templates. Сохранены BGE-M3/Qdrant retrieval, RAGContextBuilder, контрольные вопросы/ожидания, active Fixed/Structure, Top-K, right file scope, executor и Recognition Viewer.
2. **Builder.** `application/full_document.py::FullDocumentContextBuilder` возвращает text/document_id/file/title/page_count/included_pages/token_count/status, бюджетные оценки и provenance. Это reader канонического документа, не retrieval engine.
3. **Канонический текст.** По записи документа в snapshot текущего ProcessingRun читается `normalized_documents[recognition_version]`; для legacy — `documents[document_id]` с проверкой версии и принадлежности recognition IDs этому run. Используются `Document.blocks`, порядок `(page_number, reading_order, block_id)`, page markers `[PAGE N]`. Raw OCR text не используется. Неполные/неподходящие версии явно отклоняются.

6. **Qdrant.** В Full Document не вызывается. Чанки не участвуют в сборке полного документа.
7. **Бюджет.** `[llm].full_document_context_budget = 32768` — общий разрешённый бюджет, включая input и reserved output. ## Контракт MiniMax и конфигурация

Контракт сверён с официальной документацией 30.09.2026: [OpenAI-compatible API](https://platform.minimax.io/docs/api-reference/text-openai-api), [Chat Completions](https://platform.minimax.io/docs/api-reference/text-chat-openai), [коды ошибок](https://platform.minimax.io/docs/api-reference/errorcode).

POST `https://api.minimax.io/v1/chat/completions`, Bearer authorization; модель `MiniMax-M2.7`. Передаются `messages`, `temperature`, `max_completion_tokens`, `stream=false`, `reasoning_split=true`. Читаются `choices[0].message.content`, `finish_reason`, whitelisted token usage. Обрабатываются HTTP ошибки и `base_resp.status_code`. `max_completion_tokens` включает reasoning; `length` сохраняется как TRUNCATED, в том числе при пустом финальном тексте. Внутреннее reasoning не выводится и не сохраняется.

`config.toml`, секция `[llm]`: provider, api_base, model, api_key_env, timeout=120, temperature=1.0, max_output_tokens=8192, context_budget=12000. Ключ хранится только в окружении процесса. `.env` исключён из Git, но **автоматической загрузки `.env` нет**.

Чтобы запустить сервер с ключом, остановите текущий экземпляр и выполните в PowerShell из корня проекта:

```powershell
$miniMaxSecret = Read-Host 'MINIMAX_API_KEY' -AsSecureString
$env:MINIMAX_API_KEY = [System.Net.NetworkCredential]::new('', $miniMaxSecret).Password
Remove-Variable miniMaxSecret
.\.venv\Scripts\python.exe -m rag_arbiter web
```

Ключ не нужно присылать в чат, писать в исходники или TOML. `READY` означает наличие настройки, а не успешный сетевой запрос; ошибка последней генерации отражается в статусе. Переменную должен унаследовать именно процесс веб-сервера.

CLI использует тот же сервис:

```powershell
.\.venv\Scripts\python.exe -m rag_arbiter rag 'Ваш вопрос' --run-id d6575efd47b349f1a8a733bb2bc50d2c --strategy structure --top-k 5
```

Для одного документа добавьте `--document-id`; CLI сохраняет сравнение в той же SQLite. Повторная генерация не гарантирует побитово одинаковый ответ облачной модели: воспроизводимость обеспечивается сохранёнными параметрами, индексом, точным контекстом и результатом.

## Отчёт по 31 пункту задания

1. **Day 21 reuse.** Сохранены `Pipeline.resources`, `SemanticRetriever.retrieve_vector`, `BgeM3EmbeddingProvider`, `LocalVectorStore`, `ResultsService`, `RunService`, его executor/operation lock, активные версии из `RechunkService`, SQLite JSON metadata, Recognition Viewer и правая панель файлов. OCR, нормализация и chunkers не переписывались. Исходный semantic search остаётся отдельным раскрываемым блоком.
2. **LLMProvider.** `rag_arbiter/llm.py`: stateless `generate(LLMRequest) -> LLMResult`; результат содержит text/provider/model/duration_ms/usage/status/error/finish_reason.
3. **MiniMax provider.** HTTPS JSON request через стандартный urllib, ключ разрешается только перед отправкой. HTTP redirect запрещён, чтобы не пересылать Authorization другому адресу. Ошибки возвращаются безопасными кодами, без raw response/exception body.
4. **Модель.** `MiniMax-M2.7`, явно в конфигурации и обоих результатах. Название сверено с официальным API; это выбранная поддерживаемая модель, не утверждение о самой новой модели MiniMax.
5. **Конфигурация.** `[llm]` в `config.toml`; секрет — `MINIMAX_API_KEY`. Для старых ProcessingRun настройки генерации берутся из текущей конфигурации и фиксируются при создании сравнения; параметры корпуса и embeddings сохраняются из исходного run.
6. **Secret.** В исходниках, UI, записях сравнений и обычных логах ключа нет. Тест проверяет HTTP ответы/SQLite с искусственным секретом; отдельный тест проверяет редактирование случайного отражения ключа в ответе. Провайдер логирует только модель/длительность/статус/usage/код ошибки.
7. **NO_RAG.** Один запрос: одинаковая базовая system instruction + исходный вопрос. Нет пустого source block, чанков, ожиданий, предыдущих ответов и истории вопросов.
8. **RAG.** NO_RAG сохраняется сразу; затем поиск, ContextBuilder и второй независимый вызов MiniMax. Ошибка одной ветки не удаляет успешную другую, итог PARTIAL. Нет источников — EMPTY_RETRIEVAL без подмены ответом NO_RAG.
9. **BGE-M3 → Qdrant.** Через существующие ресурсы Pipeline кодируется только `[question]`; existing SemanticRetriever обращается к Qdrant и каноническим чанкам SQLite. Документные embeddings не пересоздаются. Qdrant закрывается до освобождения operation lock; сетевой вызов MiniMax не держит этот lock.
10. **Fixed/Structure.** Selector `RAG INDEX` выбирает ровно одну стратегию для сравнения; default Structure Aware. Старый Fixed vs Structure raw search сохранён.
11. **Active ChunkingRun.** При enqueue фиксируется snapshot выбранного активного индекса, включая существующие partitions от частичного rechunk. Проверяется ID из UI; устаревший ID отклоняется. Сервис не смешивает произвольные версии. Композитный активный индекс сохраняет предусмотренные Day 21 версии разных документов.
12. **Scope.** `selectedDocument` из правой панели передаётся в API. All Documents — активный корпус; документ — пересечение document_ids каждой активной partition с выбранным ID, фильтр выполняется в Qdrant. Чужой документ отклоняется.
13. **Top-K.** Default 5; строгое целое 1–10, проверяется API и сервисом. Финальный Top-K применяется после объединения результатов активных partitions.
14. **ContextBuilder.** Целые чанки в порядке score, исключение одинаковых ID и точного content hash; metadata + text. Не добавлен reranker или сложный overlap deduplicator.
15. **Sources.** `[S1]`, `[S2]` и далее. В контексте reference/file/title/section/pages/text; в сохранённых sources также chunk_id, score, document_id и проверенные recognition IDs. Контекст рассматривается как данные, а не инструкции.
16. **Budget.** `context_budget` ограничивает консервативную оценку: число UTF-8 bytes всей собранной строки, включая headers/separators. `context_tokens` — **оценка, не точный tokenizer MiniMax**; метод явно сохраняется и подписан в UI. Чанк, не помещающийся целиком, пропускается. `retrieved_count` и `used_count` различаются. Фактический usage MiniMax хранится отдельно. Бюджет контекста не включает вопрос/system instruction; их размер ограничен отдельно.
17. **Panels.** Две равные колонки desktop; на узком экране вертикально. Каждая показывает модель, статус, длительность и текст/ошибку. Под RAG — retrieval stats и источники; длинные тексты/технические параметры раскрываются отдельно.
18. **Control questions.** SQLite `rag_evaluation_questions`, максимум 10 active. Короткие строки с ellipsis, без раскрытия. Question/expected_answer/expected_sources/order/active/timestamps сохраняются в существующем JSON-подходе; expected_sources — JSON array внутри записи.
19. **Click.** Нажатие текста подставляет вопрос и создаёт новое сравнение со snapshot ожиданий. Нажатие строки истории/результата пакета открывает уже сохранённое сравнение, без повторной генерации.
20. **Delete.** × выставляет active=false; история остаётся, освобождается место для нового вопроса. Проверка лимита и вставка выполняются одной SQLite write transaction.
21. **Expectations.** Отдельное небольшое modal окно по ✎, а также при добавлении. Expected sources редактируются как валидируемый JSON: ID/filename/chunk ID, optional page range/section. Ожидания показаны у выбранного ответа и не отправляются LLM.
22. **Run All.** Один существующий executor последовательно обрабатывает frozen список активных вопросов, одинаковые индекс/настройки/scope. SQLite `rag_batches` сохраняет IDs/current/total/completed/failed/partial/status. UI обновляется лёгким polling; повторное открытие из истории восстанавливает отображение пакета. Новый scheduler не добавлен.
23. **Persistence.** SQLite schema 6 добавляет три JSON metadata tables без удаления Day 21. `rag_comparison_runs` хранит вопрос, scope, модель, generation settings, base prompt/version, индекс snapshot/ID, Top-K, embedding identity, retrieved/used IDs, контекст и sources, ответы/usage/durations/status/errors/timestamps. Внутренние config/index snapshots и owner PID не выдаются публичным endpoint. Незавершённые задания умершего процесса становятся INTERRUPTED.
24. **Metrics.** source_hit@1, @3, @5 по совпадению хотя бы одного заданного expected source с retrieved source; optional страницы пересекаются, section проверяется как подстрока. При Top-K меньше порога — значение не вычисляется. Без expected sources метрики отсутствуют. Ожидаемые источники не задают правильность текста ответа.
25. **LLM judge.** Не добавлен, semantic grading отсутствует.
26. **NO_RAG isolation.** Проверено capture request: только system и question, без chunks и history.
27. **Selected context only.** RAG передаёт только принятый ContextBuilder текст; весь корпус, raw PDF, изображения, expected answer и история не отправляются.
28. **Fairness.** Один provider/config snapshot, одинаковые model/temperature/max_completion_tokens/base system/остальные generation fields; меняется только наличие контекста перед тем же вопросом.
29. **Real test.** MiniMax credentials отсутствуют, реального облачного comparison нет. Выполнена реальная BGE-M3/Qdrant часть, сохранены NOT_CONFIGURED для обеих веток. Ответы модели и ссылки в её тексте не проверяются автоматическим судьёй. Бюджет генерации включает reasoning; при length результат явно отмечается TRUNCATED. Day 23 не реализовывался.

## API

- `GET/POST /api/rag/questions`, `PUT/DELETE /api/rag/questions/{id}`.
- `POST /api/runs/{run_id}/rag/compare`: question или question_id, document_id nullable, strategy, top_k, optional chunking_run_id.
- `POST /api/runs/{run_id}/rag/batch`: те же retrieval settings, все active questions.
- `GET /api/rag/comparisons/{id}`, `GET /api/rag/batches/{id}`.
- `/ui/rag/...` — HTML fragments для того же UI; write-запросы сохраняют existing origin/`X-RAG-Request: 1` guard.
