==================================================
2. ROOT CAUSE HTTP 503
==================================================

В предыдущем E2E:

CREATE_NEW → INDEXED

REPLACE_EXISTING → INDEXED

Но последующий /consult запрос
завершился HTTP 503.

Причина исторического ответа неизвестна.

НЕЛЬЗЯ:

- угадывать её;
- объявлять проблему исправленной
  только по отсутствию воспроизведения;
- увеличивать timeout без диагностики;
- автоматически повторять дорогой E2E.

Последовательность:

1. Изучить сохранённые trace.
2. Проверить фактический Registry.
3. Проверить canonical content.
4. Проверить active version.
5. Проверить Qdrant/index.
6. Проверить RetrievalPolicy и ACL.
7. Проверить маршрутизацию Chat/RAG.
8. Проверить обработку исключений.
9. Найти фактический источник 503.

При необходимости выполнить
один ограниченный воспроизводящий запрос
с полноценным exception traceback.

Ввести безопасный correlation ID
для диагностики.

Различать:

AUTH_ERROR
DOCUMENT_UNAVAILABLE
INDEX_NOT_READY
RETRIEVAL_ERROR
PROVIDER_ERROR
TIMEOUT
INTERNAL_ERROR.

Если причина не установлена,
фиксировать UNVERIFIED.

Не подменять технический сбой
отсутствием документов.

5. PLANNER STABILIZATION
==================================================

Наблюдавшиеся проблемы:

- TRUNCATED generation;
- INVALID NextTool JSON;
- context budget exceeded;
- неустойчивое завершение задач;
- незавершённая validation.

Стабилизировать существующий Planner.

Не создавать новый Agent.

Использовать typed tool calls
с проверяемой схемой.

Проверять:

- допустимое имя инструмента;
- обязательные аргументы;
- типы;
- состояние задачи;
- пользовательские права;
- существование нужных файлов;
- tool budget;
- context budget;
- общий deadline.

LLM не должна вызывать
несуществующие инструменты.

Неисполняемый вызов не должен
разрушать ранее сохранённый результат.

==================================================
7. RESPONSE / CONTEXT BUDGET
==================================================

Не решать проблему одним
увеличением max_tokens.

Перед модельным вызовом:

- оценить размер данных;
- учитывать output capacity;
- ограничивать размер tool response;
- использовать ссылки на workspace
  вместо повторения полных документов;
- передавать компактное состояние задачи;
- не дублировать citations;
- не передавать в Planner
  весь предыдущий tool trace.

Полный trace хранится отдельно.

В случае недостаточного бюджета:

- сохранить прогресс;
- остановиться с понятным PARTIAL;
- не делать бесконечные retry.

Предусмотреть ограниченное восстановление
невалидного typed tool call,
если это безопасно и укладывается
в ресурсный бюджет.

==================================================
8. CANCEL / TIMEOUT
==================================================

Проверить:

- отмену задачи;
- общий deadline;
- deadline отдельного вызова;
- освобождение блокировок;
- завершение background operations;
- исключение двойного выполнения;
- восстановление состояния после сбоя.

Если вызов MiniMax уже выполняется,
учесть фактические возможности
его отмены в текущем transport.

После timeout новая задача
не должна получать вечный BUSY.

Не освобождать блокировку ценой
одновременного выполнения
двух конфликтующих операций.

Для каждого документального утверждения:

- subject;
- predicate;
- object;
- source document;
- source version;
- evidence blocks;
- validation result.

Использовать существующие
GroundingValidator и EvidenceReview,
а не новый semantic engine.

Проверять соответствие
утверждения и его доказательства.

Не считать точную цитату
автоматическим доказательством
сформулированного вывода.
