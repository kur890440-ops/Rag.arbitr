ЗАДАЧА

Реализовать Day 31:

подключение сетевых папок через MCP,
поиск новых и измененных документов,
передачу их в существующий ingestion
и интерфейс управления источниками.

==================================================
1. INSPECT FIRST
==================================================

Сначала изучи реальную архитектуру:

- ingestion entrypoints;
- document registry;
- canonical SQLite storage;
- document identity;
- OCR/normalization pipeline;
- chunking/indexing;
- background execution/resume;
- existing MCP integrations;
- config;
- FastAPI/Jinja2/HTMX UI;
- existing tests.

Не создавать дублирующие компоненты.

До реализации определить точную точку,
через которую внешний документ
попадает в существующий ingestion.

==================================================
2. MCP CONNECTOR
==================================================

Реализовать настоящий MCP server/client
по существующим project conventions.

Предусмотреть read-only операции:

list_sources
list_directory
scan_source
get_file_metadata
read_file / read_file_chunk

Названия адаптировать к реализации MCP SDK.

Для больших документов поддержать
потоковое или порционное чтение,
не передавать огромные PDF
одним JSON-ответом MCP tool.

MCP отвечает за доступ к источнику.

SyncService отвечает за сравнение
состояний и организацию обработки.

Existing Ingestion отвечает
за содержимое документов.

==================================================
3. NETWORK PATHS
==================================================

Поддержать:

Windows UNC:
\\server\share\folder

Mounted paths:
Z:\Documents
или системные mount paths.

Работать через текущие права ОС.

Не добавлять отдельный SMB-протокол,
если стандартная файловая система
уже предоставляет нужный доступ.

==================================================
4. SOURCE REGISTRY
==================================================

Через существующую SQLite создать
реестр сетевых источников.

Минимум:

id
name
root_path
enabled
recursive
scan_interval
include_patterns
exclude_patterns
last_scan_at
last_success_at
status
last_error.

Использовать существующие
storage/repository conventions.

Не создавать вторую БД.

==================================================
5. ROOT SECURITY
==================================================

Каждый источник ограничен
явно разрешенным root.

Запретить:

- path traversal;
- чтение за пределами root;
- обход через symlink/junction;
- произвольное чтение системных файлов;
- открытие пользовательского пути,
  не входящего в allowlist.

Не предоставлять LLM
неограниченный файловый доступ.

==================================================
6. FILE DISCOVERY
==================================================

Обходить каталоги рекурсивно,
если recursive=true.

Использовать поддерживаемые проектом
форматы документов.

Минимально ориентироваться на:

PDF
DOCX

Остальные форматы определять
по фактическим возможностям ingestion.

Игнорировать временные
и служебные файлы.

Применять include/exclude patterns.

Ошибку одной папки
не превращать в сбой всего сервиса.

==================================================
7. CHANGE DETECTION
==================================================

Хранить состояние обнаруженных файлов.

Ключ идентификации:

source_id + normalized relative path

с учетом правил конкретной ОС.

Metadata fingerprint:

size
modification time

и content hash там,
где он необходим для подтверждения изменений.

Не использовать filename
как единственный идентификатор.

Статусы:

NEW
MODIFIED
UNCHANGED
MISSING
ERROR.

==================================================
8. FILE STABILITY
==================================================

Не индексировать документ,
который еще записывается на NAS.

Проверять:

- стабильный размер;
- стабильное modification time;
- отсутствие изменения при чтении.

Использовать bounded retry.

Если файл нестабилен:

DEFERRED / RETRY_LATER.

Не маркировать его FAILED навсегда.

==================================================
9. INCREMENTAL SYNC
==================================================

Первый scan:
обнаружить все документы.

Следующий scan:
передавать в ingestion
только NEW/MODIFIED.

UNCHANGED:
никакой повторной обработки.

MISSING:
пометить в source registry,
но не удалять автоматически
из canonical storage/Qdrant.

Если сеть недоступна:
scan ERROR,
а не массовый MISSING.

==================================================
10. EXISTING INGESTION REUSE
==================================================

Для нового файла:

MCP discovery
→ sync decision
→ existing ingestion entrypoint.

Не создавать отдельные:

OCR processor
PDF parser
chunker
embedding pipeline
indexer.

Использовать существующие
SUCCESS/PARTIAL/FAILED semantics,
page resume и provider diagnostics.

Для MODIFIED соблюдать текущую модель
версий документов и переиндексации.

Не оставлять устаревшие chunks
активными как новую версию документа.

==================================================
11. DEDUPLICATION
==================================================

Повторный scan не должен
создавать копии одного документа.

Не допускать одновременного
ingestion одного source-file version.

При одинаковых файлах
в разных источниках
сохранять корректный provenance.

Переиспользовать existing dedup logic,
если она существует.

==================================================
12. BACKGROUND PROCESSING
==================================================

Сканирование и ingestion
не должны блокировать Web UI.

Использовать существующий
background execution/job mechanism.

Не создавать отдельный scheduler,
если в проекте уже есть подходящий.

Нужны:

- cancellation;
- ограниченная concurrency;
- progress;
- error isolation;
- повторение после transient failure.

Поддержать ручной scan независимо
от автоматического расписания.

19. SOURCE PROVENANCE
==================================================

Использовать существующие

В существующем document registry
показывать source metadata,
но не перестраивать весь UI.

==================================================
21. TESTS
==================================================

Добавить автоматические проверки:

A. Первый scan обнаруживает документы.

B. Повторный scan неизмененных файлов
не вызывает ingestion.

C. Новый файл обнаруживается.

D. Измененный файл обнаруживается.

E. Копируемый/нестабильный файл
откладывается.

F. Недоступный сетевой источник
не превращает файлы в MISSING.

G. Исчезнувший файл
не удаляется из RAG автоматически.

H. Нельзя выйти за пределы root.

I. Symlink/junction escape запрещен.

J. Большой каталог
не приводит к unbounded memory usage.

K. Один файл
не индексируется одновременно дважды.

L. MCP calls используют
реальный MCP protocol.

M. Sync вызывает
существующий ingestion entrypoint.

N. OCR/chunking/indexing
не дублируются.

O. Existing Search/Chat
продолжают работать.
