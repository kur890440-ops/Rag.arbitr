@PROJECT:rag.арбитр

@L3:DAY34_DOCUMENT_WORKSPACE_AND_PUBLISHING
@PRESERVE

ЗАДАЧА

Реализовать Day34:
ассистента для автономной работы
с документами архива с возможностью
публикации обратно в сетевой архив.

Использовать существующую архитектуру.

==================================================
1. INSPECT FIRST
==================================================

Перед разработкой исследуй:

- existing Chat;
- /consult;
- MiniMax provider;
- existing tool orchestration, если есть;
- Day31 MCP / SMB;
- Source Registry;
- SyncService;
- canonical SQLite;
- ingestion;
- document versions Day32;
- Point RAG / Exhaustive;
- RetrievalPolicy;
- Telegram authentication;
- user roles and ACL;
- существующие механизмы работы
  с DOCX, PDF и другими файлами.

Проверь реальные возможности записи
в сетевые источники.

Не предполагай наличие write access
без фактической проверки.

Составь короткий технический план
по существующим модулям.

==================================================
2. FILE TOOL CONTRACTS
==================================================

Реализовать контролируемые операции:

search_documents
read_document
analyze_documents
create_document
edit_document
compare_documents
validate_document
save_workspace_result
prepare_publication
confirm_publication

Использовать typed input/output.

Каждый вызов получает
authenticated user context.

Не создавать универсальный
execute_shell/write_any_file.

Доступ к документам — только после ACL.

==================================================
3. TASK ORCHESTRATION
==================================================

Пользователь задаёт цель.

Например:

"Найди все подходящие договоры,
сравни обязанности и подготовь
заключение в Word".

Система самостоятельно определяет
последовательность доступных операций.

Использовать MiniMax
и существующую инфраструктуру
планирования, если она имеется.

Не создавать отдельный Agent
или второй генеративный pipeline.

Предусмотреть ограничения:

- число tool calls;
- глубина выполнения;
- время;
- ресурсные бюджеты;
- отмена;
- обработка ошибок;
- частичные результаты.

Не допускать бесконечных циклов.

==================================================
4. SEARCH / READ
==================================================

Использовать существующие:

Document Registry
Canonical Content
MCP Day31
RetrievalPolicy
RAG / Exhaustive.

Для чтения конкретного документа
закреплять version ID.

Для работы с несколькими файлами
сохранять исходный набор документов.

Нельзя молча исключать документы
из анализа при технических ошибках.

Нельзя использовать top-k
как полный корпус exhaustive.

==================================================
5. DOCUMENT WORKSPACE
==================================================

Создать минимальный WorkspaceService.

Хранить:

Task
WorkspaceFile
SourceReference
FileRevision
Diff
ValidationResult
PublicationRecord

Переиспользовать существующие
таблицы и типы, если подходят.

Файлы физически хранить
в контролируемой рабочей директории.

Метаданные — в существующей SQLite.

Рабочие области изолированы
по authenticated user ID.

Не использовать исходные сетевые
файлы в качестве черновиков.

==================================================
6. CREATE DOCUMENT
==================================================

Поддержать создание:

DOCX
PDF
TXT
Markdown

В первую очередь обеспечить
качественный DOCX.

Использовать существующие
библиотеки, когда возможно.

Для документов по шаблону
сохранять доступные стили,
поля, таблицы и структуру.

Добавлять ссылки на исходные документы
там, где они нужны для подтверждения
содержательных выводов.

Созданный файл должен действительно
существовать и открываться.

==================================================
7. EDIT DOCUMENT
==================================================

Изменять рабочую копию.

Для DOCX:

- не удалять нецелевые разделы;
- сохранять поддерживаемые стили;
- сохранять таблицы;
- сохранять колонтитулы;
- сохранять нумерацию;
- контролировать структуру.

Проверять результат после сохранения.

Если формат невозможно безопасно
отредактировать, сообщить ограничение.

Не преобразовывать оригинальный DOC
или PDF с перезаписью исходника.

==================================================
8. DOCUMENT DIFF
==================================================

Использовать механизм Day32,
если он применим.

Сравнивать:

- разделы;
- абзацы;
- списки;
- таблицы;
- существенные реквизиты.

Различать:

ADDED
REMOVED
MODIFIED
MOVED

Хранить сравниваемые версии.

Diff показывать в существующем Chat
в компактном виде.

Полный diff доступен как результат задачи.

==================================================
9. ARCHIVE PUBLISHER
==================================================

Создать минимальный ArchivePublisher
для контролируемой записи в архив.

Не добавлять произвольную запись
в существующий Day31 MCP.

Работать только с разрешёнными
источниками и корневыми папками.

Отдельно проверять техническое
право записи сервисной учётной записи.

Операции:

CREATE_NEW
REPLACE_EXISTING

Никаких неявных перезаписей.

==================================================
10. PUBLICATION PREPARE
==================================================

Перед подтверждением:

1. Проверить роль ADMIN.
2. Проверить целевой source.
3. Проверить разрешённый root.
4. Нормализовать путь.
5. Исключить path traversal.
6. Проверить symlink/reparse-point
   escape и обход через UNC.
7. Проверить формат документа.
8. Проверить результат validation.
9. Проверить исходную версию.
10. Получить текущий hash оригинала.
11. Подготовить diff.
12. Сохранить неизменяемый
    publication proposal.

Proposal должен закреплять:

- user ID;
- draft file ID;
- SHA-256 draft;
- target source/path;
- operation;
- expected original version/hash;
- diff revision;
- срок действия.

LLM не может самостоятельно
подтверждать публикацию.

==================================================
11. PUBLICATION CONFIRM
==================================================

Публикация только после
явного действия администратора.

Перед фактической записью:

- повторно проверить ADMIN;
- повторно проверить ACL;
- проверить неизменность draft;
- проверить неизменность target;
- проверить expected hash;
- проверить срок и статус approval.

При изменении target:

CONFLICT

Не перезаписывать его.

Для CREATE_NEW:
не заменять существующий файл.

Для REPLACE_EXISTING:
сохранить предыдущую версию
до операции.

Использовать staged write
во временный файл целевой папки
и безопасную публикацию.

Учитывать ограничения SMB:
атомарность rename/replace
не предполагать без проверки.

Обеспечить восстановление
при частичной ошибке.

Повтор запроса с тем же
idempotency key не должен
публиковать файл второй раз.

==================================================
12. PUBLICATION AUDIT
==================================================

Фиксировать:

Who
When
Task ID
Target source
Target path
Operation
Previous hash
New hash
Previous version
Publication result
Error / conflict reason

Секреты и содержимое документов
не записывать в общие application logs.

==================================================
13. DAY31 / DAY32 SYNC
==================================================

После успешной публикации:

- зафиксировать PUBLISHED;
- инициировать или использовать
  существующий автоматический sync;
- обнаружить NEW/MODIFIED;
- обработать stable-file condition;
- запустить обычную ingestion;
- обновить canonical SQLite;
- обновить Qdrant;
- зарегистрировать новую версию;
- сохранить Day32 diff/review.

Не создавать второй индексатор.

Не заставлять пользователя
нажимать кнопку обновления.

Отображать реальные состояния:

PUBLISHED_PENDING_INDEX
PROCESSING
INDEXED
INDEX_FAILED

Использовать существующие
статусы Registry/SyncService,
не дублировать их без необходимости.

При ошибке ingestion публикация
не должна ошибочно считаться INDEXED.

==================================================
14. UI
==================================================

Использовать существующий Chat.

Показывать:

- найденные документы;
- прогресс задачи;
- созданные файлы;
- diff;
- validation;
- ограничения полноты;
- ссылку для скачивания;
- статус публикации.

Кнопка подтверждения публикации
должна быть связана
с конкретным publication proposal.

Backend проверяет её независимо
от UI и сообщений MiniMax.

Не создавать дополнительный
файловый менеджер.

Не заставлять пользователя вручную
выбирать каждый следующий tool call.

==================================================
15. AUTHORIZATION
==================================================

ADMIN:

- чтение разрешённых документов;
- создание;
- редактирование;
- публикация;
- замена с подтверждением.

CLIENT:

- чтение разрешённых документов;
- создание личных документов;
- редактирование личных черновиков;
- скачивание результатов.

CLIENT не может:

- публиковать в архив;
- изменять оригиналы;
- управлять workspace другого клиента;
- обходить source grants.

Проверить IDOR, CSRF и session isolation.

Не давать MiniMax менять роли
или самостоятельно одобрять операции.

==================================================
16. DAY33 INTEGRITY
==================================================

Реальный E2E Day33 пока имеет FAIL.

Не считать неподтверждённые результаты
достоверными только потому,
что они записаны в DOCX.

При неполном анализе:

- сохранять подтвержденные факты;
- отмечать непроверенные документы;
- показывать ограничения;
- не выдавать частичный результат
  за полный.

Публикация аналитического заключения
с существенными пробелами
должна требовать отдельного
явного принятия этих ограничений
администратором.

Это не отменяет необходимости
исправлять Day33 отдельно.

==================================================
17. SECURITY TESTS
==================================================

Проверить:

- CLIENT не публикует;
- ADMIN публикует;
- approval нельзя подделать;
- approval нельзя использовать повторно;
- просроченный approval отклоняется;
- изменённый draft отклоняется;
- изменённый target даёт CONFLICT;
- CREATE_NEW не перезаписывает;
- path traversal запрещён;
- symlink/reparse-point escape запрещён;
- источник вне allowlist запрещён;
- пользователь не читает чужой workspace;
- неудачная запись не портит оригинал;
- ошибка синхронизации видна;
- публикация не нарушает версии Day32.

==================================================
18. REAL E2E SCENARIO A
==================================================

В существующем Chat:

"Найди субагентские договоры,
сравни условия отчётности
и подготовь документ DOCX".

Ассистент должен:

1. Самостоятельно найти документы.
2. Прочитать минимум 3 реальных файла.
3. Проверить данные.
4. Подготовить DOCX.
5. Сохранить рабочий результат.
6. Проверить файл.
7. Вернуть доступный результат в Chat.

Проверить содержимое DOCX,
а не только его существование.

==================================================
19. REAL E2E SCENARIO B
==================================================

В существующем Chat:

"Возьми подготовленное заключение,
добавь раздел с различиями
и сохрани новую редакцию".

Ассистент должен:

1. Найти соответствующий документ.
2. Создать рабочую копию.
3. Выполнить изменение.
4. Сохранить исходное оформление.
5. Построить diff.
6. Вернуть изменённый DOCX.
7. Сохранить provenance.

==================================================
20. REAL E2E SCENARIO C
==================================================

Использовать выделенную тестовую папку
реального разрешённого SMB-источника.

Не публиковать тесты в рабочие
договоры без явного разрешения.

1. ADMIN выбирает готовый документ.
2. Получает publication proposal.
3. Видит целевой путь и diff.
4. Подтверждает публикацию.
5. Система записывает файл в архив.
6. Проверяет файл на SMB.
7. Day31 обнаруживает изменение.
8. Ingestion завершается.
9. Новая версия доступна через Registry.
10. Документ находится через Chat/RAG.

Отдельно проверить REPLACE_EXISTING
и конфликт параллельной модификации.

Если доступной тестовой SMB-папки нет,
отметить live SMB E2E как NOT RUN.
Не подменять его тестом локальной папки.

==================================================
24. ACCEPTANCE
==================================================

Day34 считается завершённым, когда:

- ассистент сам работает с файлами;
- читает несколько документов;
- создаёт реальный DOCX;
- редактирует рабочую копию;
- сохраняет оформление;
- формирует diff;
- возвращает файлы в Chat;
- ADMIN может подтвердить публикацию;
- файл реально записывается на SMB;
- новая версия автоматически
  обнаруживается и индексируется;
- конфликт версий защищён;
- права CLIENT соблюдены;
- результаты воспроизводимы.

Unit tests недостаточны
для подтверждения полноценного E2E.
