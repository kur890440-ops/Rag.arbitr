3. ОДИН КАНОНИЧЕСКИЙ TOOL CALL
==================================================

Определи единственный контракт
структурированного вызова инструмента.

Сначала проверь, какую форму
действительно поддерживает
текущий MiniMax transport.

Не добавляй оболочку поверх
структуры, которую provider
уже генерирует самостоятельно.

Выбери одну каноническую схему,
например:

NextTool:
    operation
    arguments
    completion_status

Это концептуальный пример,
не обязательная новая Pydantic-модель.

Предпочитай существующие типы.

Обеспечь:

- одну согласованную schema
  на входе provider;
- один контракт в production decoder;
- запрет extra fields;
- запрет неизвестных операций;
- строгую проверку arguments;
- проверку состояния задачи;
- проверку прав пользователя.

Исторические форматы использовать
для offline replay и миграционной
совместимости только если она
реально необходима.

Не превращать parser
в коллекцию догадок о JSON.

==================================================
5. PLANNER ERROR HANDLING
==================================================

При INVALID_TOOL_CALL:

- сохранить trace;
- сохранить уже созданные файлы;
- не выполнять невалидную операцию;
- зафиксировать точный reason;
- разрешить максимум одну безопасную
  попытку исправления;
- при повторном отказе завершить PARTIAL.

При TRUNCATED:

- не выполнять неполный JSON;
- не выполнять частичную мутацию;
- сохранить checkpoint;
- не увеличивать лимиты автоматически.

При CONTEXT_BUDGET_EXCEEDED:

- сохранить прогресс;
- использовать компактное состояние;
- не передавать повторно
  полный tool trace и документы.

Нельзя повторно выполнять
завершённую неидемпотентную операцию.
