@PROJECT:rag.арбитр

@L3:DAY33_PUBLIC_CONSULTANT
@PRESERVE

ЗАДАЧА

Реализовать Day33:

публичного AI-консультанта
по страховым документам.

Использовать существующий RAG
и уже подключенную MiniMax.

Не создавать второй RAG,
второй ingestion или
независимый Agent backend.

==================================================
1. ОБЯЗАТЕЛЬНЫЙ СЦЕНАРИЙ
==================================================

Посетитель открывает:

/consult

Без регистрации.

Задает вопрос по страхованию.

Ассистент:

1. Понимает смысл вопроса.
2. Учитывает контекст диалога.
3. Определяет необходимость RAG.
4. Получает разрешенные документы,
   если они нужны.
5. Передает контекст MiniMax.
6. Формирует естественный ответ.
7. Подтверждает документальные выводы.
8. Поддерживает уточняющий разговор.

Никаких технических команд
от клиента не требуется.

==================================================
2. INSPECT FIRST
==================================================

Изучи существующие:

- Chat orchestration;
- ChatSession;
- ReferenceResolver;
- DialogueWorkingContext;
- RetrievalPolicy;
- AnswerModeRouter;
- Point RAG;
- Exhaustive;
- ContextBuilder;
- MiniMax GenerationProvider;
- grounding/citations;
- canonical document storage;
- Source Registry;
- document versioning;
- FastAPI/Jinja2/HTMX;
- configuration;
- tests.

Определи, что реально можно
переиспользовать.

Не придумывай параллельные
компоненты без необходимости.

==================================================
3. PUBLIC KNOWLEDGE SCOPE
==================================================

Добавить явное разрешение
публикации документов.

Использовать существующую
canonical storage/metadata model.

Документ по умолчанию:

PRIVATE.

Только администратор
через внутренний интерфейс
может разрешить публикацию.

Например:

PUBLIC / PRIVATE

При необходимости связывать
разрешение с конкретной версией.

Не публиковать автоматически
все файлы сетевого источника.

Новые и измененные документы
не должны становиться публичными
без явного решения администратора.

Отзыв разрешения должен
немедленно исключать документ
из новых запросов публичного Chat.

==================================================
4. HARD RETRIEVAL FILTER
==================================================

Все запросы /consult
должны ограничиваться
разрешенными документами.

Фильтр применять:

ДО candidate_top_n.

Проверить:

Point RAG
Exhaustive
follow-up
source navigation
citation resolution.

Не допускать fallback
на приватный корпус.

Не полагаться на инструкцию LLM
"не показывай приватные документы".

Фильтрацию реализовать
на уровне данных и RetrievalPolicy.

==================================================
5. GENERATION PROVIDER
==================================================

Использовать существующий
MiniMax GenerationProvider.

Не создавать новый MiniMax client,
если действующий подходит.

Все этапы, которым требуется
генеративная LLM, должны
использовать MiniMax.

В том числе:

- semantic routing;
- answer generation;
- repair при необходимости.

Ollama/Qwen в публичной
генеративной цепочке не использовать.

Не менять модели и настройки
внутреннего Search/Chat.

==================================================
6. THREE MODES
==================================================

Ввести или адаптировать typed mode:

GENERAL
DOCUMENT
MIXED.

GENERAL:

Вопрос не требует знания
конкретных договоров.

Пример:
"Что такое страховая премия?"

MiniMax отвечает непосредственно.

DOCUMENT:

Вопрос требует содержимого
опубликованных документов.

Пример:
"Какие исключения предусмотрены
этими правилами страхования?"

Использовать existing RAG.

MIXED:

Вопрос требует общего объяснения
и конкретных условий.

Пример:
"Что такое франшиза
и как она применяется
по вашим правилам?"

Использовать MiniMax + RAG.

==================================================
7. ROUTING
==================================================

Переиспользовать существующий
semantic/typed router.

Не строить маршрутизацию
исключительно на ключевых словах.

Учитывать:

- текущий вопрос;
- последние сообщения;
- текущие референты;
- выбранную тему.

При сомнении, содержит ли вопрос
утверждение об условиях конкретного
договора, предпочитать DOCUMENT/MIXED.

Router не должен получать
доступ к приватным документам.

==================================================
8. CONVERSATION CONTEXT
==================================================

Реализовать временные
анонимные ChatSession.

Использовать существующие
компоненты диалогового контекста.

Сохранять:

- тему разговора;
- последние вопросы;
- подтвержденные референты;
- относящиеся к разговору источники;
- необходимые уточнения.

Не переносить в публичный Chat
внутреннюю память другого пользователя.

Ограничивать историю
по token budget.

Применять TTL и автоматическую
очистку анонимных сессий.

Не использовать IP
как единственный идентификатор сессии.

==================================================
9. FOLLOW-UP
==================================================

Пример:

Клиент:
"Какие случаи покрывает страховка?"

Ассистент:
отвечает по опубликованным документам.

Клиент:
"А если управляющий допустил ошибку?"

Ассистент должен правильно связать
новый вопрос с предыдущей темой.

Клиент:
"А когда могут отказать?"

Ассистент продолжает обсуждение
тех же условий.

Не выполнять новый независимый поиск,
игнорируя контекст разговора.

Но при изменении вопроса
или области документов
перепроверять источники.

История ответа не заменяет
документальные доказательства.

==================================================
10. RESPONSE QUALITY
==================================================

Создать versioned system prompt
для публичного консультанта.

Требования:

- естественный русский язык;
- понятные объяснения;
- без избыточного юридического жаргона;
- краткий прямой ответ;
- подробности по необходимости;
- отсутствие ненужных повторений;
- уточнение существенной неоднозначности;
- честное признание ограничений.

Не превращать каждый ответ
в формальное юридическое заключение.

При этом не упрощать содержание
до искажения юридического смысла.

==================================================
11. FACTUAL BOUNDARIES
==================================================

Четко различать:

A. Общие сведения MiniMax.

B. Положения опубликованных документов.

C. Предположения или возможные
   интерпретации.

Для B обязательны
подтверждающие источники.

Нельзя утверждать:

"По вашему договору предусмотрено..."

без фактической проверки договора.

Если документ не содержит ответа,
сообщить об этом.

Допустимо дать общее объяснение,
но явно отделить его
от документально подтвержденного.

==================================================
12. GROUNDING
==================================================

Переиспользовать существующий
grounding/citations pipeline.

Для DOCUMENT/MIXED:

- документальные claims;
- source IDs;
- evidence quotes;
- validation;
- максимум один repair
  согласно existing contract.

Для GENERAL:

не требовать искусственных цитат
из отсутствующего RAG-контекста.

Однако запретить выдавать
общие знания за подтвержденные
договорные положения.

Не создавать второй grounding engine.

==================================================
13. PUBLIC SOURCE NAVIGATION
==================================================

В ответах по документам показывать:

- название документа;
- положение/страницу/блок;
- короткую цитату.

Переход к источнику
должен использовать
публичный read-only маршрут.

Не открывать через цитаты
внутренний document viewer
без проверки публикации.

Не раскрывать:

- UNC paths;
- private document IDs;
- внутренние metadata;
- приватные версии;
- административные ссылки.

==================================================
14. WEB UI
==================================================

Создать отдельную публичную страницу:

GET /consult

Использовать существующий stack:

FastAPI
Jinja2
HTMX/SSE
CSS.

В интерфейсе:

- заголовок:
  "Консультант по страхованию";

- история сообщений;

- ответы с форматированием;

- компактные цитаты;

- поле ввода;

- индикатор обработки;

- понятные ошибки.

Не показывать:

- технические настройки RAG;
- source selector приватных баз;
- диагностику;
- Task Memory;
- MCP tools;
- внутренние административные вкладки.

==================================================
15. SESSION UX
==================================================

При открытии /consult
анонимная сессия создается
без регистрации.

Посетитель может вести
последовательный диалог.

Не смешивать разговоры
разных посетителей.

Историю хранить с ограничением
по сроку и объему.

Предусмотреть краткое
уведомление, что вопросы
обрабатывает AI через MiniMax,
а тексты сообщений передаются
внешнему LLM-провайдеру.

Не запрашивать персональные данные,
если они не требуются.

==================================================
16. SECURITY
==================================================

Поскольку /consult публичный:

- никаких административных операций;
- никакого произвольного MCP;
- никакого доступа к filesystem;
- никакого ingestion;
- никакого изменения документов;
- никаких приватных источников.

Проверять на сервере
все права публикации.

Ограничивать входной текст
и размер LLM payload.

Не логировать пользовательские
сообщения целиком без необходимости.

Корректно экранировать
рендеримый Markdown/HTML.

==================================================
17. ABUSE / COST CONTROL
==================================================

Добавить через существующий
config/rate-limit mechanism:

- ограничение запросов;
- ограничение параллельности;
- max input/output tokens;
- timeout;
- ограничения длины истории;
- bounded anonymous sessions;
- контроль расхода MiniMax.

При превышении возвращать
понятную клиенту ошибку.

Ограничения IP/session
не считать абсолютной защитой
от обхода через новые сессии.

Не допускать бесконечных retries
и автоматического роста расходов.

==================================================
18. KNOWLEDGE STATES
==================================================

Если опубликованных документов нет:

GENERAL продолжает работать.

DOCUMENT/MIXED:

- не искать в приватной базе;
- не придумывать условия;
- сообщать об отсутствии
  доступных подтверждающих документов.

Если документ опубликован,
но еще не проиндексирован:

не объявлять его доступным
для документального ответа.

Если источник удален из публикации:

он не должен появляться
в новых ответах и citations.

==================================================
19. TEST DIALOGUES
==================================================

Подготовить минимум 12–15
тестовых реплик,
объединенных в несколько диалогов.

Проверить:

A. Приветствие.

B. Общий страховой термин.

C. Вопрос по опубликованным правилам.

D. Уточняющий вопрос.

E. Смена темы.

F. Возврат к предыдущей теме.

G. Смешанный GENERAL + DOCUMENT.

H. Сравнение двух документов.

I. Вопрос с недостатком данных.

J. Попытка узнать приватный документ.

K. Два независимых посетителя.

L. Несколько одновременных запросов.

M. Prompt injection внутри документа.

N. Отзыв публикации документа.

O. Ошибка или timeout MiniMax.

==================================================
20. EVALUATION
==================================================

Оценивать не только
успешность HTTP-запроса.

Для каждого теста фиксировать:

- выбранный режим;
- сохранение контекста;
- смысловую корректность;
- наличие выдуманных условий;
- точность цитат;
- соблюдение public scope;
- время ответа;
- результат grounding;
- ошибки.

Часть диалогового качества
оценивать вручную.

Не объявлять ответы хорошими
только потому, что JSON валиден.

==================================================
21. LIVE E2E
==================================================

Провести реальный тест
на опубликованном
страховом документе.

1. Открыть /consult
   в анонимном браузере.

2. Задать общий вопрос.

3. Получить ответ MiniMax.

4. Задать вопрос по документу.

5. Проверить цитаты.

6. Задать 2 уточняющих вопроса.

7. Сменить тему.

8. Проверить изоляцию
   второго посетителя.

9. Попробовать запросить
   неопубликованный документ.

10. Проверить rate limit.

Если платный MiniMax вызов
нельзя выполнить в окружении,
не выдавать mock за live E2E.

Не публиковать реальные внутренние
документы без явного разрешения.
