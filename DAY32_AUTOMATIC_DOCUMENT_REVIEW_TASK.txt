@PROJECT:rag.арбитр

@L3:DAY32_AUTOMATIC_DOCUMENT_REVIEW
@PRESERVE

ЗАДАЧА

Реализовать автоматический
анализ новых и измененных
PDF/DOCX документов.

Это адаптация Day32:
AI Code Review → AI Document Review.

==================================================
1. ОБЯЗАТЕЛЬНЫЙ СЦЕНАРИЙ
==================================================

Новый/измененный файл на SMB/NAS
→ автоматический MCP scan
→ SyncService
→ existing ingestion
→ сохранение версии
→ normalizing/indexing
→ summary или diff/review
→ автоматическое отображение в Chat.

Не требовать ручного запуска.

==================================================
2. INSPECT FIRST
==================================================

Перед реализацией изучи:

- Source SyncService;
- MCP Connector;
- Document Registry;
- current version/fingerprint logic;
- canonical SQLite;
- Docling;
- ingestion/version handling;
- chunking/indexing;
- RAG;
- Local/Cloud GenerationProvider;
- Day31 notifications;
- Chat source scope;
- source navigation.

Особенно проверь:

Сохраняются ли предыдущие
версии измененных документов?

Не предполагай, что сохраняются.

Определи минимальное изменение
существующей архитектуры.

==================================================
3. DOCUMENT VERSIONING
==================================================

Если текущая реализация
перезаписывает старую версию,
добавить immutable version storage.

Минимум:

document_id
version_id
source_id
relative_path
content_hash
source_fingerprint
created_at
canonical_content_reference
ingestion_status.

Для сравнения должны быть доступны
две полные нормализованные версии.

Не изменять старую версию
при повторном ingestion.

Не смешивать версии в активном индексе.

Существующие citations должны
оставаться привязанными
к исходной версии.

==================================================
4. NEW DOCUMENT SUMMARY
==================================================

Для NEW после успешной нормализации
и индексации:

- получить canonical content;
- выполнить существующий
  LocalLLMProvider;
- сформировать краткое резюме.

Поля:

document_name
document_type
summary
key_provisions
important_dates
important_amounts
obligations
attention_points
source_references.

Не использовать RAG вместо
самого текста анализируемого файла.

Для больших документов
использовать существующие
механизмы чанков и контролируемой
агрегации с сохранением доказательств.

==================================================
5. STRUCTURED DOCUMENT DIFF
==================================================

Для MODIFIED:

загрузить Version A и Version B.

Нормализовать структуру:

headings
paragraphs
numbered clauses
lists
tables.

Определять:

ADDED
REMOVED
MODIFIED
MOVED.

Сопоставлять блоки
по структуре и содержимому,
а не исключительно
по порядковому номеру.

Изменение нумерации
не должно автоматически
превращать все последующие пункты
в удаленные и добавленные.

==================================================
6. LEGAL CHANGES
==================================================

Особенно выделять:

- изменение сторон;
- изменение предмета договора;
- изменение обязанностей;
- изменение ответственности;
- изменение порядка оплаты;
- изменение процентов/сумм;
- изменение сроков;
- добавление исключений;
- удаление условий;
- изменение порядка расторжения.

Это классификация
уже обнаруженных изменений.

Не считать классификацию LLM
доказательством факта изменения.

==================================================
7. TABLE DIFF
==================================================

Сравнивать таблицы
с сохранением связи:

строка
→ столбец
→ значение.

Например:

Было:
Агентское вознаграждение — 5%.

Стало:
Агентское вознаграждение — 3%.

Результат:

MODIFIED
5% → 3%.

Не превращать таблицы
в несвязанный текст.

==================================================
8. LLM REVIEW
==================================================

Structured Diff
→ существующий GenerationProvider.

LLM формирует:

- краткое резюме изменений;
- существенные изменения;
- возможные последствия;
- вопросы, требующие внимания.

LLM должна использовать
только подтвержденные изменения
и разрешенный контекст.

Отделять установленные факты
от предполагаемых последствий.

Не выполнять юридически значимые
действия автоматически.

==================================================
9. PROVENANCE
==================================================

Каждое изменение содержит:

document_id
old_version_id
new_version_id
old_block_id
new_block_id
change_type
old_text
new_text
section
confidence/status.

Если соответствие блоков
не удалось установить достоверно,
помечать UNCERTAIN.

Не скрывать неопределенность.

==================================================
10. AUTOMATIC EXECUTION
==================================================

Использовать существующий
background execution mechanism.

При появлении новой версии
создать задачу review.

Не запускать повторно,
если для пары версий
review уже существует.

Использовать idempotency key:

document_id
+ old_version_id
+ new_version_id
+ review_version.

Ошибки review не должны
отменять успешную индексацию.

==================================================
11. CHAT INTEGRATION
==================================================

Использовать существующий Chat UI.

Для NEW:

"Добавлен документ:
Агентский договор.docx.

Краткое содержание: ..."

Для MODIFIED:

"Изменен документ:
Агентский договор.docx.

Добавлено: N пунктов.
Удалено: N пунктов.
Изменено: N пунктов."

Ниже:

[Подробные изменения]

Это дополнительная информация,
а не новый Chat backend.

Не создавать новую вкладку.

==================================================
12. SOURCE SCOPE
==================================================

Соблюдать выбранные источники Chat.

Для фиксированного набора документов:

- NEW — предлагать включение
  по ранее согласованному Day31 flow;

- MODIFIED — показывать новую версию
  и предлагать обновить используемую
  версию документа.

Не изменять фиксированный scope
без подтверждения пользователя.

Не затрагивать другие ChatSession.

==================================================
13. INDEX VERSION CONSISTENCY
==================================================

Для нового RAG-запроса
использовать корректную активную
версию документа.

Не смешивать chunks разных версий
как один документ.

При ошибке индексации
не объявлять новую версию готовой.

Сохранить возможность проверки
старых цитат по старой версии.

==================================================
14. ERROR HANDLING
==================================================

Обработать:

VERSION_NOT_AVAILABLE
DIFF_FAILED
AMBIGUOUS_BLOCK_MATCH
DOCUMENT_TOO_LARGE
REVIEW_GENERATION_FAILED
INDEX_NOT_READY.

Если предыдущая версия отсутствует,
не утверждать, что пункты добавлены
или удалены.

Показать:
"Предыдущая версия недоступна
для сравнения."

==================================================
15. TESTS
==================================================

Обязательно проверить:

A. Новый DOCX → summary.

B. Измененный DOCX → diff.

C. Добавление пункта.

D. Удаление пункта.

E. Изменение суммы или процента.

F. Перемещение пункта.

G. Перенумерация пунктов.

H. Изменение таблицы.

I. Только форматирование изменено.

J. UNCHANGED → review не запускается.

K. Старые версии сохраняются.

L. Старые citations остаются корректными.

M. Новая версия не смешивается
   со старой в retrieval.

N. Повторное событие
   не создает дубликат review.

O. Ошибка LLM не ломает ingestion.

P. Chat показывает результат автоматически.

Q. Source scope соблюдается.

R. Existing PDF/DOCX/RAG tests проходят.

==================================================
16. REAL E2E
==================================================

Использовать разрешенную
тестовую сетевую папку.

Подготовить DOCX Version A
с известными пунктами.

Дождаться автоматического scan.

Проверить:

- NEW;
- ingestion;
- INDEXED;
- summary в Chat.

Заменить документ на Version B:

- удалить один пункт;
- добавить один пункт;
- изменить один процент.

Дождаться автоматического scan.

Проверить:

- MODIFIED;
- сохранение Version A;
- создание Version B;
- корректный structured diff;
- LLM review;
- отображение в Chat.

Повторить scan без изменений.

Проверить отсутствие
повторного анализа.

Не выдавать MOCK за REAL E2E.

==================================================
17. REPORT
==================================================

Создать:

DAY32_DOCUMENT_REVIEW_RESULTS.md

Включить:

- проверку текущего versioning;
- изменения модели хранения;
- алгоритм diff;
- пример NEW summary;
- пример MODIFIED diff;
- точные старые/новые фрагменты;
- результаты индексации;
- результаты Chat notification;
- результаты тестов;
- ограничения.

Не включать конфиденциальные
документы целиком.

==================================================
18. ACCEPTANCE
==================================================

Day32 выполнен, если:

- новые документы автоматически
  получают краткое резюме;

- измененные документы автоматически
  сравниваются с предыдущей версией;

- добавленные/удаленные/измененные
  пункты определены корректно;

- LLM объясняет смысл изменений;

- отчет появляется в Chat;

- старые версии сохраняются;

- повторные scan не создают
  повторные ревью;

- полноценный E2E подтвержден.

==================================================
19. FINAL REPORT
==================================================

Кратко сообщи:

1. Что было с versioning.
2. Какие изменения внесены.
3. Как работает diff.
4. Как анализируются таблицы.
5. Как формируется LLM review.
6. Где выводится результат.
7. Как сохраняются старые версии.
8. Как защищены citations.
9. Результаты E2E.
10. Результаты tests.
11. Оставшиеся ограничения.

После выполнения ОСТАНОВИСЬ.

Не добавлять GitHub PR integration.
Не создавать второй ingestion,
второй RAG или второй Chat.
