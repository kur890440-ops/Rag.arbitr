ЗАДАЧА

Исправить семантическое понимание вопросов
во внутреннем консультанте /consult.

НАБЛЮДАЕМАЯ ПРОБЛЕМА

Вопрос:

"С кем заключены субагентские договоры?"

Ассистент возвращает список файлов
и их метаданные вместо извлечения
сторон из содержания договоров.

Это функциональная ошибка маршрутизации
и/или использования существующего RAG.

==================================================
1. ОБЯЗАТЕЛЬНЫЙ РЕЗУЛЬТАТ
==================================================

На вопрос:

"С кем заключены субагентские договоры?"

Ассистент должен:

1. Найти все подходящие документы
   в разрешенном корпусе.

2. Прочитать их нормализованное содержание.

3. Установить стороны и роли сторон.

4. Извлечь субагентов.

5. Определить номера и даты договоров,
   если они указаны.

6. Сопоставить найденные сведения.

7. Исключить дублирование.

8. Вернуть полный подтвержденный перечень
   с цитатами.

Никаких ручных выборов маршрута
или дополнительных команд пользователя.

==================================================
2. INSPECT FIRST
==================================================

Перед изменениями исследуй:

- /consult handler;
- текущий semantic routing;
- AnswerModeRouter;
- ArchiveStatusProvider;
- existing Point RAG;
- existing Exhaustive;
- ReferenceResolver;
- DialogueWorkingContext;
- RetrievalPolicy;
- document registry;
- canonical content;
- DOC/DOCX normalization;
- MiniMax provider;
- grounding/citations.

Установи точную причину,
почему содержательный вопрос
получил ответ в стиле ARCHIVE.

Не пытайся исправить проблему
одним hardcoded условием
на слово "субагентский".

==================================================
3. SEMANTIC INTENT ROUTING
==================================================

Переиспользовать существующий
typed AnswerModeRouter.

Различать:

GENERAL
ARCHIVE
POINT_RAG
EXHAUSTIVE
MIXED

Адаптировать к существующим enum/contracts.

Примеры:

"Сколько у тебя документов?"
→ ARCHIVE

"Какие субагентские договоры есть?"
→ ARCHIVE

"С кем заключены субагентские договоры?"
→ EXHAUSTIVE

"Кто субагент по договору №123?"
→ POINT_RAG

"Какие обязанности у этих субагентов?"
→ reference-aware document analysis

"Что означает субагентский договор?"
→ GENERAL

"Что означает субагентский договор
и какие обязанности указаны в наших?"
→ MIXED/EXHAUSTIVE по смыслу.

Использовать MiniMax для семантического
определения намерений, если это необходимо.

Не создавать keyword/regex router
для конкретных формулировок.

==================================================
4. REUSE EXHAUSTIVE
==================================================

Для полных перечней использовать
существующий exhaustive pipeline.

Не создавать новый exhaustive engine.

Проверить:

- corpus eligibility;
- source scope;
- active document versions;
- normalized content readiness;
- обработку всех подходящих документов;
- map/extraction;
- deterministic merge;
- финальный synthesis.

Не использовать Qdrant top-k
как ограничение полного перечня.

Не допускать скрытого перехода
к Point RAG при неудачном exhaustive.

==================================================
5. DOCUMENT ELIGIBILITY
==================================================

При определении подходящих документов:

- учитывать document type, если известен;
- учитывать metadata;
- использовать содержание документа;
- учитывать выбранный source scope.

Названия файлов допустимы
для поиска кандидатов,
но не для подтверждения фактов.

Документ с названием "Отчет..."
не считать договором автоматически.

Документ без слова "договор" в названии
не исключать автоматически,
если содержание подтверждает нужный тип.

Не объявлять непроверенные кандидаты
подтвержденными договорами.

==================================================
6. STRUCTURED EXTRACTION
==================================================

Для подтвержденных договоров
использовать typed extraction result.

Conceptually:

ContractPartyExtraction:

document_id
document_version_id
is_relevant_contract
contract_type
contract_number
contract_date
subagent_name
other_party_name
party_roles
evidence_blocks
evidence_quotes
extraction_status

Статусы:

CONFIRMED
PARTIAL
NOT_FOUND
AMBIGUOUS
DOCUMENT_UNREADABLE

Не заполнять отсутствующие поля
выдуманными значениями.

Существующий extraction/claim model
переиспользовать, если он подходит.

==================================================
7. EXTRACTION GROUNDING
==================================================

Каждое установленное имя контрагента
должно подтверждаться
фрагментом исходного документа.

Проверять:

- существование source ID;
- наличие текста цитаты;
- соответствие версии документа;
- правильность роли стороны.

Особенно важно:

не путать субагента,
агента, принципала и страховщика.

Если имя встречается в документе,
это еще не доказывает,
что организация является
стороной договора.

==================================================
8. MERGE / DEDUPLICATION
==================================================

Сопоставлять результаты по:

document identity
version
contract number/date
parties

с учетом доступности реквизитов.

Разные версии одного договора
не считать двумя независимыми
договорами без обоснования.

Не объединять разных контрагентов
только по похожему названию.

При неоднозначности сохранять
несколько записей с отметкой
о необходимости проверки.

==================================================
9. FINAL ANSWER
==================================================

Для вопроса о субагентах
формировать содержательный ответ.

Пример структуры:

"По проанализированным договорам
установлены следующие субагенты:"

Субагент
Договор
Другая сторона
Подтверждающий источник

Потом:

Проверено документов: N
Подтверждено договоров: N
Установлено субагентов: N
Неполных/неоднозначных: N

Все значения — фактические.

Не выводить технические данные:

INDEXED
source_id
timestamp
internal IDs

вместо содержательного ответа.

При неполном результате
не подменять его общим отказом:
дать подтвержденную часть
и обозначить ограничения.

==================================================
10. FOLLOW-UP CONTEXT
==================================================

Обязательно проверить последовательность:

Q1:
"С кем заключены субагентские договоры?"

Q2:
"Какие обязанности предусмотрены
у этих субагентов?"

Q3:
"У кого отличаются условия отчетности?"

После Q1 сохранять
typed referents найденных сторон
и договоров через существующий
DialogueWorkingContext/ReferenceResolver.

Q2 должен анализировать
подтвержденные договоры из Q1.

Q3 должен сравнивать условия
по соответствующим договорам.

Не заменять referents
предположениями MiniMax.

При смене scope
перепроверять допустимость источников.

==================================================
11. OTHER MODES
==================================================

Сохранить:

GENERAL:
обычные объяснения MiniMax.

ARCHIVE:
реальный состав архива
из Document Registry.

POINT_RAG:
конкретные факты.

MIXED:
общие сведения + документальные факты.

Не отправлять каждый вопрос
в дорогостоящий exhaustive.

Не создавать отдельную систему
маршрутизации только для /consult,
если общий router расширяем безопасно.

==================================================
12. DIAGNOSTICS
==================================================

Для каждого тестового запроса
фиксировать:

- исходный вопрос;
- выбранный intent/mode;
- причину маршрутизации;
- eligible document count;
- inspected document count;
- confirmed contract count;
- extraction statuses;
- extracted party count;
- dedup count;
- citation/grounding status;
- generation time;
- errors.

Показывать диагностику
в существующем внутреннем trace/export.

Публичный/клиентский UI
не перегружать служебными полями.

13. TESTS
==================================================

Добавить regression tests:

A. "Какие договоры есть?"
   → ARCHIVE.

B. "С кем заключены договоры?"
   → DOCUMENT/EXHAUSTIVE,
   не список имен файлов.

C. Один договор
   → правильные стороны.

D. Несколько договоров
   → полный перечень.

E. Два договора с одной стороной
   → корректное объединение.

F. Название файла содержит имя стороны,
   но текст его не подтверждает
   → имя не выдумывается.

G. Название не содержит имя стороны,
   но текст содержит
   → сторона извлекается.

H. Документ без извлекаемого текста
   → PARTIAL/UNREADABLE.

I. Отчет/акт рядом с договорами
   → не становится договором
   только из-за похожего имени.

J. Источники и цитаты
   соответствуют canonical content.

K. Повторные версии
   не создают ложные дубликаты.

L. Три последовательных вопроса
   сохраняют referents.

M. Смена темы работает.

N. Source scope соблюдается
   на всех этапах.

O. GENERAL/ARCHIVE/POINT_RAG
   не сломаны.

P. Existing internal Chat
   продолжает работать.

14. REAL E2E
==================================================

Использовать реальный индексированный
корпус Day31 и настоящую MiniMax.

Выполнить:

1.
"С кем заключены субагентские договоры?"

2.
"Какие обязанности предусмотрены
у этих субагентов?"

3.
"У кого отличаются условия отчетности?"

Проверить вручную по исходным DOC/DOCX:

- правильность определения сторон;
- полноту анализа;
- номера/даты;
- отсутствие выдуманных контрагентов;
- правильность цитат;
- сохранение контекста.

Отдельно выполнить:

"Какие субагентские договоры есть?"

и убедиться, что этот вопрос
действительно маршрутизируется в ARCHIVE.

Если полный реальный E2E недоступен,
отметить NOT RUN
и точную причину.

Не выдавать mock-тесты
за реальную проверку качества.
