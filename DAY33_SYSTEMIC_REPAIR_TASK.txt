==================================================
3. MULTI-SPAN EVIDENCE
==================================================

Один факт может подтверждаться
несколькими фрагментами документа.

Например:

Блок 1:
ФИО стороны.

Блок 2:
Роль стороны.

Блок 3:
Дата и номер договора.

Не требовать, чтобы все сведения
обязательно содержались в одной цитате.

Использовать связанные canonical spans
одной версии документа.

Каждый атомарный факт должен иметь
достаточный набор доказательств.

Проверять соответствие:

лицо → роль → договор → источник.

Нельзя подтверждать роль человека
только потому, что его имя
упоминается где-то в документе.

==================================================
4. IMMUTABLE SOURCE TEXT
==================================================

MiniMax не должна перепечатывать
оригинальный текст доказательств.

Модель выбирает:

- canonical block ID;
- span ID или точные offsets;
- принадлежность факта;
- необходимые связанные фрагменты.

Исходный текст подставляет приложение.

Для выбранного доказательства:

1. Проверить существование ID.
2. Проверить версию.
3. Получить исходный текст.
4. Проверить соответствие факту.
5. Сформировать citation.

Не допускать исправления грамматики,
перефразирования или изменения
исходных цитат моделью.

В частности, ошибка вида:

"Предоставлять Агентом"
    →
"Предоставлять Агенту"

не должна уничтожать доказательства.

Оригинальная формулировка документа
должна сохраняться буквально.

==================================================
5. FIELD-LEVEL VALIDATION
==================================================

Для договоров проверять отдельно:

- тип договора;
- субагента;
- агента;
- роли сторон;
- номер договора;
- дату договора.

Сведения из разных canonical blocks
можно объединять при доказанной связи.

Разделить поля:

ESSENTIAL:
тип договора, стороны, роли сторон.

OPTIONAL:
номер, точная дата, иные реквизиты.

Отсутствие необязательного поля
не должно исключать договор,
если необходимые факты подтверждены.

Например:

У Ханина неполная дата.

Это не основание исключать
подтвержденного субагента из перечня.

Статус:

CONFIRMED
PARTIAL
AMBIGUOUS
UNSUPPORTED
TECHNICAL_ERROR

Должен относиться к конкретному факту
или полю, а не бесконтрольно
распространяться на весь документ.

==================================================
6. PARTIAL BATCH RECOVERY
==================================================

Исправить D2.

Сейчас одна неточная цитата
может уничтожить весь пакет
из множества фактов.

Это недопустимо.

Реализовать item-level validation.

Если пакет содержит:

23 корректных факта
1 некорректный факт

то:

23 корректных сохраняются;
1 некорректный отклоняется
или отправляется на ограниченное
восстановление доказательства.

Если общий ответ пакета невозможно
разобрать, допускается ограниченный
повтор соответствующего пакета,
а не всего exhaustive.

Не снижать требования к доказательствам.

Не считать ошибочные факты истинными.

Не изменять исходный текст цитат.

Сохранять точные причины отказа.

==================================================
7. EXHAUSTIVE COVERAGE
==================================================

Исправить D1, D3, D8.

Разделить три понятия:

A. Scope coverage:
сколько документов входит
в допустимый корпус.

B. Processing coverage:
сколько документов успешно обработано.

C. Answer completeness:
насколько полно установлены
запрошенные факты.

Не считать:

37/38 обработанных документов

эквивалентом:

37/38 найденных договоров.

Не считать:

3 найденных договора из 5

полным ответом только потому,
что большинство документов обработано.

Для каждого документа сохранять:

document_id
version
eligibility
processing_status
extraction_status
evidence_status
contribution_to_answer

Если документ не удалось обработать,
не превращать это в отсутствие факта.
